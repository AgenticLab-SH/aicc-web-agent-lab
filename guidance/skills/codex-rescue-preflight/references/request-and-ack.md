# 작업 단위 복구 준비 요청과 확인 기준

## 적용 시점
Codex 자신의 통신·도구·실행 환경을 끊을 수 있는 **구체적인 한 번의 유지보수** 직전에만 발동한다. 기능 이름이 비슷해도 `전송 가능`, `대기 수락`, `독립 복구 가능`, `복구 후 기존 작업 재개 가능`은 서로 다른 상태다.

## 중단 사전 안내

AICC·OCX·Codex 업데이트/재시작·설치·경로 변경 등으로 현재 대화나 작업 연결이 잠시라도 끊길 수 있으면, 실제 중단 조작 **전에 매번** 사용자에게 다음 내용을 commentary로 출력한다. 파일 기록·내부 계획·승인 질문만으로 대신하지 않는다. 이미 승인된 작업에 새 승인을 요구하는 절차는 아니다.

- 변경 대상과 끊길 수 있는 대화/도구·작업 범위.
- 예상 단절 시간과 **예상 완료 시각 또는 시각 범위(KST)**. 설치뿐 아니라 재연결·필수 실제 확인까지 포함하고 보장이 아닌 추정임을 밝힌다.
- 진행 중 요청 종료 등 시간 예측이 불가능한 대기는 완료 시각 미정이라고 쓰고, 조건 충족 후 소요 예상 및 다음 안내 시점을 함께 제시한다. 대기를 숨기거나 완료 시간을 지어내지 않는다.
- 자동 복구/롤백 여부, 기다릴 시간, 복구되지 않을 때 기존 정확한 대화를 재개하는 방법. 불명 원 요청을 다시 보내라는 지시를 하지 않는다.

예: “OCX 실행본을 교체해 현재 대화가 잠시 끊길 수 있습니다. 예상 단절은 30~90초, 재연결·확인 포함 완료는 14:20~14:23 KST 예상입니다. 독립 복구 작업자가 실패 시 원본으로 되돌립니다. 14:23 이후에도 복구되지 않으면 같은 대화를 다시 열어 ‘재개’라고 보내세요. 원 작업을 새 대화에 복제하지 마세요.” 실제 작업의 최근 관측·크기에 맞춰 시간을 산정하고 이 예시 시간을 고정값으로 쓰지 않는다.

오래 대기했거나 대상/시간이 달라졌으면 마지막 변경 직전에 갱신해 출력한다. ETA를 넘겼으면 연결 가능한 즉시 이유·현재 상태·새 ETA 또는 미정 사유를 알린다. 복귀 후에는 실제 적용·재연결·미완료를 관측 근거로 보고한다. health만으로 성공이나 원 응답 복구를 주장하지 않는다. 사전 안내가 기존 READY·유휴·작성권·보안 경계를 대신하지 않는다.

## 실제 지원되는 도구에만 맞춘 요청 예시

아래 필드는 **개념적인 계약**이며 존재하지 않는 API의 JSON 인자로 전달하지 않는다. 도구의 실제 스키마가 우선한다.

| 필드 | 뜻 |
|---|---|
| owner_task_id | 원래 Codex 작업의 정확한 ID |
| request_id | 이 요청만 식별하는 값 |
| challenge | 요청과 응답을 연결하는 일회용 확인 값. 인증 토큰이 아님 |
| target | 변경 대상 서비스·경로·설치본 |
| risk | 어떤 실패로 통신이 끊길 수 있는지 |
| allowed_recovery | 승인된 확인·복구 동작의 정확한 목록 |
| rollback_ref | 복귀 가능한 이전 상태의 위치 |
| expires_at | 대기 효력의 종료 시점 |

## 준비 판정

`READY` 판정에는 모두 필요하다.

1. 제공자가 보증하는 **실제 수신·수락 응답**. 스스로 생성한 JSON·테스트 픽스처·이전 로그는 불가.
2. `owner_task_id`, `request_id`, `challenge`, `target`, `allowed_recovery`가 요청과 일치함.
3. 만료되지 않았고 대상 작업의 실제 실행 동안 유효함.
4. 문제 발생 시 계속 남는 독립적인 실행 경로와 권한이 있음. 동일한 실패 원인에 의존하면 불합격.
5. 복구 대상의 정확한 소유권, 이미 진행 중인 요청, 원본 상태가 조회 가능함. 미확인 상태를 강제로 정상으로 변경하지 않음.
6. 지원된다면 작은 무변경 시험 결과가 있음.

검증되지 않으면 `REQUESTED`, `UNAVAILABLE`, `HOLD` 중 실제 상태로 기록하고 본 작업의 자기단절 가능 단계는 시작하지 않는다.

## 상태 흐름

`NOT_REQUIRED` (무해한 작업) 또는 `NEEDS_RESCUE -> REQUESTED -> READY -> MAINTENANCE -> POSTCHECK -> CLOSED`.

복구 필요 시 `MAINTENANCE -> INCIDENT -> INDEPENDENT_RECOVERY -> RECONCILE -> POSTCHECK`.

`REQUESTED`에서 응답하지 않거나 권한/안전 검토가 거부되면 `HOLD`로 전환하며 승인되지 않은 대체 자동화를 만들지 않는다.

## 검증 시나리오

| 상황 | 판정 |
|---|---|
| 요청을 보내지 않았지만 연결 포트가 살아 있음 | `NOT_READY` |
| Web GPT가 “알겠습니다”라고 한 번 응답했으나 독립 작업자가 없음 | `NOT_READY` |
| 대기 응답이 왔지만 현재 재시작할 서비스와 같은 경로에 의존 | `NOT_READY` |
| 다른 작업 ID 또는 만료된 응답 | `NOT_READY` |
| 승인된 독립 실행 담당자가 정확한 범위로 수락하고 가벼운 확인 통과 | `READY` |
| 실제 작업 결과가 불확실한데 같은 요청을 다시 실행하려 함 | `HOLD`, 먼저 상태 대조 |
| 정책·도구가 자동 대기를 금지 | `HOLD`, 대체 수단으로 우회 금지 |

## 정리

Codex의 작업이 정상 종료되면 준비 요청은 해제하거나 만료 처리한다. 상시 실행·암묵적인 리스닝·시간 제한 없는 감시는 이 절차의 범위가 아니다.

## 기존 서비스의 첫 정비 교체

이전 서비스에 호출자 목록이나 drain API가 없다는 사실과 실제 실행 중인 작업은 구분한다.
관측하지 못한 요청 수를 `0`으로 만들지 않으며, 과거 결과 미확인만으로 승인된 정비를 영구 차단하지 않는다.

- 사용자가 해당 연결의 정비·교체를 승인했고, 실제로 알려진 실행 작업을 완료하거나 중단 범위 밖에
  보존했으면 정확한 서비스 범위의 한 번의 계획 정비 중단을 사용할 수 있다. 전체 PC·다른 Codex·다른
  브라우저의 idle는 그 대상에 포함되지 않는다. 확인된 실행 작업이나 소유권 미확인은 이 분기로 넘기지 않는다.
- 강제 종료 명령이나 Task 종료를 정상 drain이라고 부르지 않는다. 중단 전 정확한 Task와 프로세스
  생성시각·명령·자식 범위, 원본 백업, 독립 복구 READY를 결속하고, 새 자식·소유권 변화가 있으면 중단하지 않는다.
  정상 drain 증명이 없는 중단은 `planned-maintenance-stop`으로 기록한다.
- 옛 호출자·결과의 전체 목록을 읽을 수 없으면 `activeCount=null`, `unknownCount=null`,
  `lastResult=UNCONFIRMED_PRESERVED`로 남긴다. 이는 실행 작업이 없다는 증명이 아니다. 알려진 작업의
  보존 근거, 실제 사용자 정비 승인 원문, 미확인 원결과 기록과 회수 담당자를 같은 작업 ID·범위·만료에 묶는다.
- 이미 전달됐을 수 있는 원요청은 자동 재전송하지 않는다. 새 서비스가 정상이어도 옛 결과를 완료로
  바꾸지 않으며, 결과에 의존하는 후속 변경은 원래 대화·lease·작업 결과를 대조한 뒤 수행한다.
- cold 교체는 실제로 대상 Task의 재시작이 차단되고 정확한 대상 runtime이 종료된 뒤에만 적용한다.
  현재 실행 경로와 독립 복구 경로, CAS·한 번의 실행 확인·복귀 조건은 그대로 필요하다. 중단이나 적용
  결과가 불명확하면 같은 명령을 재실행하지 않고 실제 상태부터 회수한다.

## 결과 보고

일반 사용자에게 `복구 담당자 요청됨 / 독립 READY 확인됨 / 작업 완료 / 실사용 검증됨`을 단계별로 구분한다. 예: **“복구용 접속 경로는 확인했지만, 자동 대기 요청을 받을 별도 도구가 없어 위험한 업데이트는 보류했습니다.”** 이 스킬의 파일 생성·검증 자체는 복구 자동화의 실전 완료를 뜻하지 않는다.
