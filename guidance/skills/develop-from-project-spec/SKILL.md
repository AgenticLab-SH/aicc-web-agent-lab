# 에이전트 개발 준비와 명세

개발을 시작하거나 큰 변경을 계획할 때 자동으로 필요한 준비만 한다. 별도 호출·새 예약·문서 수를 늘리는 것이 목적이 아니다. 먼저 가장 가까운 지침과 기존 current·제품 명세·선택 파일의 현재 상태를 읽고, 이미 끝난 일과 남은 일을 구분한다.

## 요청의 단계부터 고정

- 아이디어/검토/설계/준비만 요청했다면 관련 문서·허용된 정리까지만 수행한다. 제품 구현·서비스 변경을 몰래 시작하지 않는다.
- 사용자가 구체적인 목표·범위의 구현을 승인했다면 필요한 준비를 보완하고 계속한다. 문서 생성이나 lifecycle 이름 자체를 새 승인 절차로 만들지 않는다.
- 불명확한 외부 효과나 결과를 크게 바꾸는 선택만 질문하고, 독립된 준비는 계속한다.
- 솔로 개발은 일정표·날짜 약속 대신 의존 순서·첫 유용한 결과·다음 행동을 사용한다. 사용자가 일정이 필요하다고 할 때만 추가한다.

## 문서는 필요한 크기로

| 작업 | 기본 준비 |
|---|---|
| 작고 명확한 수정 | 기존 current/task 또는 spec 한 곳의 결과·영향·끝난 기준. 새 문서 묶음 없음 |
| 새 기능/중간 변경 | 기존 SPEC/PRODUCT 안에 목적·범위·요구·실패/복구·완료 기준, 기존 task에 순서/담당 |
| 여러 영역·긴 작업 | 기존 specs/change의 spec·plan/tasks와 current 연결. 목적이 따로 검토돼야 하면 intent 분리 |
| 제품 전체/여러 저장소 | 제품별 정본 유지. 중앙은 연결·결정·공통 계약만 기록하고 원문을 복제하지 않음 |

파일 이름은 기존 체계를 따른다. PRD/SPEC/intent가 같은 말을 반복하면 하나를 정본으로 두고 필요한 링크만 남긴다. 없는 문서 4종을 기계적으로 만들지 않는다. 별도 intent가 필요할 때 [의도 양식](references/intent-template.md), 새 상세 spec이 필요할 때 [명세 양식](references/spec-template.md)을 사용한다.

## 개발 전 충분한 준비

데이터 진단·현업 질문 정리·기준선/정확해 비교·문맥 크기 점검이 필요하면 [로컬 개발 보조 도구](references/local-workflow-tools.md)를 선택한다. 기존 개발 스킬에 통합된 표준 라이브러리 도구이며 새 서버·MCP·에이전트를 등록하지 않는다. 필요한 명령만 실행하고 작은 수정에 전체 도구 묶음을 강제하지 않는다.

[준비와 인계](references/preparation-and-handoff.md)의 항목 중 결정에 필요한 것만 보완한다.

1. 누가 왜 쓰는지, 첫 결과, 이번/제외/나중 범위.
2. 사용자가 실제 밟는 입력→행동→결과→저장/재열기 흐름과 실패·수동 편집·중단/복구.
3. 기존 구현·사용 자료·정본/consumer·연동 경계, 필요한 schema/API·데이터 변경.
4. 선택 구조와 이유, 중요한 대안, 실제 의존·미확정·해제 조건.
5. 작은 완결 작업, 해당 Git root/편집 파일·담당·외부 효과 발신자·인수 위치.
6. 관측 가능한 완료 기준과 나중에 사용할 검사 방법. 준비 기록과 구현·설치·운영 증거는 별도.

큰 변경의 요구/완료 기준은 기존 FR/SC ID를 재사용한다. 작은 수정에 새 번호 체계를 강제하지 않는다. 선택한 첫 여정에 필수인 미확정만 막고 전제품 조사를 선행시키지 않는다.

## CI와 예약 실행의 범위

자동 검사·배포를 추가하거나 바꿀 때는 [파일 수명주기의 CI·예약 실행](references/file-lifecycle.md#ci와-예약-실행)을 적용한다. 백업·문서 변경과 제품 코드 변경의 실행 비용을 구분하고, 필요한 배포·보안 검사는 보존한다.
## 기록과 파일 관리

[파일 수명주기](references/file-lifecycle.md)를 적용한다. current는 지금 상태와 다음 행동, spec은 제품 계약, plan/tasks는 접근·순서·담당, 지침은 짧은 작업 규칙, 스킬은 재사용 절차를 소유한다. 로그·실행 영수증·개인자료는 각 소유 runtime에 남기고 HTML/Notion은 역할을 정한 링크/보기만 유지한다.

보고서·백업·latest2·final-final을 계속 신설하지 않는다. 현재 문서는 교체 갱신하고 중요한 결정은 필요한 곳에만 남긴다. 실패 기록은 반복 비용을 줄일 사례만 기존 capture-operational-knowledge로 연결한다.

## 착수·마감 경계

선택된 작업의 결과·범위·실제 의존·파일 담당·완료 판단법이 다음 에이전트에게 명확하면 준비 완료다. 개발 도중 발견한 사실은 실제 요구가 바뀌는지 판단해 정본을 고친다. 막연한 미래 위험 때문에 준비를 끝없이 늘리지 않는다.

검사/실행은 현재 모델 정책과 사용자가 명시한 범위·시점을 따른다. scripts/check_intent.py와 check_project_spec.py는 기존 양식을 쓰는 경우의 선택 도구이며 모든 작업의 gate가 아니다. 검증을 하지 않았다면 미실행으로 기록한다. source 작성만으로 요구 충족·설치·실제 작동·목표 전체 완료를 선언하지 않는다.

근거와 선택 이유는 [준비와 인계의 출처](references/preparation-and-handoff.md#출처와-선택)를 따른다.
