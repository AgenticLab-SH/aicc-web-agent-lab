# 준비와 인계

새 개발/큰 변경의 첫 세션에 사용한다. 아래는 체크할 생각의 범위이며 모든 제목을 새 파일로 만들라는 양식이 아니다.

## 최소 준비 메모

기존 SPEC/PRODUCT 또는 현재 변경 spec에 다음을 필요한 만큼 적는다.

- 목적/첫 결과: 사용자가 무엇을 입력해 어떤 유용한 결과를 받는가?
- 범위: 이번에 할 것·안 할 것·나중에 할 것과 시작 조건.
- 흐름: 실제 여는 경로→입력/선택→행동→표시→저장→재열기. 예외/취소/수동 편집/실패 뒤 재개도 의미가 있을 때 포함.
- 기존 것: 정본/원본, 현재 지원·미구현·불명, 재사용할 기능, 남길 독립 경계. 문서 주장과 실제 관측을 구분.
- 계약/설계: 필요한 interface/schema·데이터/권한/배포 소비자, 접근 선택과 대안, 이행/복구. 관계없는 전체 시스템 설계는 생략.
- 완료 기준: 정상·중요 실패 결과를 어떻게 알 수 있는지. 검사 방법과 미실행 상태. 코드/설치/실사용 인수를 분리.
- 작업: 첫 작은 여정→실제 선행→병렬 가능한 독립 단위. 날짜/공수는 요청할 때만.
- 인계: 원 task·읽을 정본·변경 파일/출력·담당·이미 완료·남은 차이·불명 전송/복구·다음 행동.

준비만 요청받으면 사용자에게 이해 가능한 결과·선택·남은 의문을 보고하고 제품 구현은 시작하지 않는다. 구현 요청은 기존 승인 범위에서 바로 잇는다. 문서가 생겼다는 이유로 재승인을 요구하지 않는다.

## 어디에 무엇을 두는가

| 자료 | 기본 위치/역할 |
|---|---|
| 제품 사용법·현재 계약 | 해당 제품 README/PRODUCT/SPEC 중 기존 정본 |
| 변경 요구·구조·작업 | 기존 specs/change 또는 제품 spec/task의 선택 절 |
| 지금 담당·미완료·다음 | context/PROJECT.md 또는 기존 제품 current |
| 오래 남을 선택 이유 | 기존 설계 결정 절. ADR은 그 결정이 독립 문서일 가치가 있을 때만 |
| 실행/배포/불명 조정 근거 | 기존 task/attempt/receipt의 owner-local 위치 |
| 재사용 문제 해결 | 해당 운영 스킬의 사례. current 수치·긴 원문 제외 |
| 전체 지도·Notion | 위 정본의 링크/의사결정/날짜 있는 보기. 코드/운영 정본을 중복 편집하지 않음 |

기존 문서 이름/폴더를 존중한다. 중앙에 모든 제품의 본문·DB·개인자료를 복사하지 않는다. 새 도구/프로세스 설치 없이 Markdown과 현재 Git·task 체계부터 활용한다.

## 요구·방법·검증 연결

현업 규칙·목적·가중치는 실제 사용자 답변/제품 정본에서 확인한다. 데이터나 논문만 보고 업무 규칙을 확정하지 않는다. 데이터가 있으면 행의 의미, 키/조인, 단위·기준 시점, 결측·중복·충돌을 분모와 함께 확인하고 원본을 자동 보정하지 않는다. 자료가 충돌하면 버전·날짜·적용 범위·권위·영향받는 입력을 대조한다. 사용자 최신 지시는 옛 키트 문안보다 우선한다.

기존 요구 ID → 실제 출처/답변 또는 가정 → 관측 가능한 완료 기준 → 설계/파일 → 실행 결과를 짧게 연결한다. 결과를 바꾸는 미확정만 질문하고 독립 작업은 계속한다. 제약·입력 크기를 먼저 정한 후 단순 기준선과 후보 방법을 비교한다. 배정/스케줄/최적화는 가능해 여부·하드 제약·목적값·작은 정확해와 차이·측정 시간을 구분한다. 복잡한 알고리즘이나 논문 채택 자체를 목표로 삼지 않는다.

실행 도구와 한계는 [로컬 개발 보조 도구](local-workflow-tools.md)를 따른다. 도구가 만드는 질문은 초안이며 실제 답변/승인/전송이 아니다. 질문 후보의 원자료 예시는 필요할 때만 노출한다.

## 주요 기능 검토와 마감

첫 입력→출력이나 핵심 기능 통합이 끝나는 단위에서 사용자에게 결과·선택 이유·실제 근거·남은 일·다음 행동을 설명한다. 기능마다 문서 묶음이나 승인을 추가하지 않는다. 검토는 파일/함수와 구체적 영향에 근거해 이름/책임/중복/실패 처리, UI·업무·입출력 경계, 상태 소유자·권한·저장/복구·변경 영향을 본다. 취향만으로 전체 재작성을 하지 않는다.

검증은 명시한 완료 기준에서 정상·빈·경계·잘못된 입력·충돌·권한·중단/복구 중 관련 경우를 고른다. 실패 입력·기대/실제·환경을 기록하고 원인 가설과 확인 원인을 구분한 뒤 최소 수리와 관련 회귀를 확인한다. 이미 통과한 검사를 근거 없이 반복하지 않는다. 설치/실행/실사용과 미실행을 구분한다.

최종 인계는 기존 명세/current에 revision·dirty, 완성/미완료·제외, 변경 파일, 실제 실행/실패/미실행, 설치·시작·중지·저장/복구, 소유 프로세스/탭, 다음 담당/한 행동을 연결한다. 읽기·결과 인수에는 새 작성권 절차를 만들지 않고 실제 쓰기충돌과 정식 원격 lease만 조정한다. 핵심 실패/복구나 필수 완료 기준이 남으면 부분 완료로 남긴다.

## 준비 완료 판단

다음 사람이 현재 목표·범위·첫 여정·필수 의존·파일 담당·끝난 기준·복구/미확정을 찾아 시작할 수 있다. 구현/운영 증거는 아직 없다고 명시한다. 모든 미래 확장·모든 저장소 분석·정확한 일정이 준비 완료 조건은 아니다.

## 출처와 선택

2026-10-20 검토. 다음 1차 자료를 참고하되 전체 프레임워크를 설치하거나 예시의 파일명·고정 병렬도·테스트 강제를 복제하지 않았다.

- [OpenAI, Harness engineering](https://openai.com/index/harness-engineering/): 짧은 AGENTS를 지도처럼 사용하고 저장소의 구조화된 지식을 정본으로 두는 사례. 이 환경에서는 짧은 공통 지침→선택 스킬→제품 정본 링크로 적용.
- [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents): 세션 사이 진행 맥락과 작은 기능 단위의 작업/증거를 남기는 사례. 새 progress 파일·초기화 스크립트를 중복 생성하지 않고 기존 current/task/Git 재사용.
- [GitHub Spec Kit](https://github.github.com/spec-kit/) 및 [Spec persistence models](https://github.com/github/spec-kit/blob/main/docs/concepts/spec-persistence.md): 명세·접근·작업의 역할과 문서 유지 방식의 선택. 기존 제품 계약을 갱신하는 방식 채택, 기능마다 4문서·새 CLI·타임라인 의무는 채택하지 않음.

소규모 솔로 개발에서는 현재 구조와 사용자 결과를 명확히 하는 데 충분한 문서만 사용한다. 이는 자료의 고정 표준이 아니라 이 환경에 맞춘 설계 판단이다.

## 지피티 운영 진입을 함께 설계

모든 제품은 지피티가 기존 README/AGENTS/PROJECT의 시작 지점에서 SPEC/PRODUCT·현재·계획과 실제 도구/CLI/API·서버 운영·권한·설정 이름·설치/실행/중지·저장/복구를 찾아 수행할 수 있도록 준비한다. 명령 예제에는 입력·출력·외부 효과·실패/불명 조정을 누적하고 비밀 값은 넣지 않는다. 기존 문서로 충분하면 새 매뉴얼을 만들지 않는다. 지피티 구성자산·코덱스 구성자산과 사용자/환경·보관·동시 작업은 AICC docs/agent-context-optimization.md의 공통 운영 계약을 따른다.

준비 단계에서 같은 파일/데이터/배포 효과의 작성자와 소유 탭/창/lease를 정하고 사용자 Chrome/앱·입력을 보존한다. 최종 삭제는 사용자와 코덱스가 함께 하므로 불필요 확정 자료는 우선 보관한다. 실제 일반 Chat+AICC 수행과 코덱스 직접 실행을 구분하고 현재 단계의 사용자 완료/검증 조건을 이후 단계로 넘어가는 기준에 반영한다.
