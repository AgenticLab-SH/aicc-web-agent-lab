# 불명 전송 조정

- 판정: 채택. 재전송보다 기존 접수와 원격 결과 조정을 먼저 한다.
- 증상/범위: 입력·업로드·저장 도구는 시간 초과했으나 실제 변경 여부가 불명인 원격 작업.
- 원인: 도구 응답 실패와 서버 미접수는 별개다. 관측된 timeout과 저장 지연의 내부 원인은 UNKNOWN이다.
- 대안 비교: 즉시 재전송은 중복 위험이 크다. 고정 대기만으로는 접수를 입증하지 못한다. 같은 대상의 기존 turn·불변 ID·논리 본문 회수가 적은 추가 작업으로 중복을 피했다. 영수증 선보존은 유용하지만 과거 ACK를 만들어 주지 않는다.
- 최소 절차: 기존 intent와 불명 상태 보존 → 원래 대상의 허용된 읽기로 조정 → 접수·저장·완료를 각각 기록. 상세는 [입력 시간 초과](../../../web-gpt-driving/references/failure-solutions.md#입력-도구의-시간-초과와-실제-접수-조정), 같은 파일의 ‘스킬 업로드의 불명 응답과 원격 ID 조정’과 ‘빈 입력창의 보내기 제어와 저장 뒤 지연’을 따른다.
- 중단/갱신: 실제 접수도 부재도 입증하지 못하면 UNKNOWN 보존. 다른 계정·새 연결·불명 요청 재전송으로 해결하지 않는다. 읽기 자체의 재시도는 미전송이 확인되고 그 경로가 허용된 경우만 별도 판단한다.
- 근거: 2026-10-16 KST 운영 영수증과 중앙 보고. 새 user turn, 원격 ID/본문 또는 제한적 저장 결과 회수가 있었으며 원래 HTTP ACK·최종 업무 완료·미래 재현성까지 입증한 것은 아니다. 원본 영수증은 소유자의 프로젝트 정본에 연결한다.

### 정상 종료 요청의 새 operation 재발신 · 2026-11-16

- 판정: 소스 수리·실제 읽기 검증, 운영 supervisor 교체 아님. `Request-AiccMobilePublicStop`에서 현재 operation 파일만 검사하면 이전 operation의 request/claim이 남아도 새 번호로 같은 종료를 보낼 수 있다. 기한 만료·claim 존재는 미전송/실패 증거가 아니다.
- 수리: 같은 runtime의 기존 요청 전체를 읽고 원 owner의 exact terminal ACK/명시적 거절이 없는 항목은 보존한다. 새 요청은 동일 request root 독점 잠금 안에서 재검사한다. 원 operation 조회는 계속 허용하고 다른 번호로 재생하지 않는다. 설치 supervisor 지원과 미결 차단을 진단·웹 화면에서 구분한다.
- 검증: pending 합성11·설치 parser11·날짜73·관리 projection17 PASS, 최종 UI 문구 검사 PASS. 실제 non-Submit 조회에서 미결 요청 보존과 registry/request/claim 무변경을 확인했다. 날짜 parser 검사의 조회 수는 추가된 요청 reader를 검토한 뒤 갱신했다. 소스 수리로 실행 중인 구형 supervisor가 바뀌거나 정상 종료 ACK/운영 설치가 생긴 것으로 보고하지 않는다. 원 요청 결과 조정·기존 정상 전환 계약은 별도다.

### Chrome 큐의 페이지 응답 유실 · 2026-11-16

- 판정: 소스·등록 확장 실행본 수리 확인. 페이지 dispatch 호출 뒤 message port 단절·응답 누락/형식 오류 또는 native dispatch ACK 유실은 전송 여부 불명이다. 예외의 `submissionUncertain` 누락을 false로 바꾸면 원 요청의 안전한 재시도 조건으로 오인될 수 있다.
- 수리: 기존 큐 background에서 페이지 호출 직전부터 실제 페이지 proof와 native ACK 처리까지 불명 경계를 유지한다. `ok:false`와 `submissionUncertain:false`를 함께 받은 명시적 전송 전 거절만 확정 실패다. 실제 page conversation/user proof를 다음 tab조회 전 저장하고, user ID없는 성공형응답도 UNKNOWN으로 보존한다. 원 prompt/claim/user proof를 보존하며 기존 실패 처리로 후속 큐를 멈춘다. 원 불명 요청은 재전송하거나 사후 확정 실패로 바꾸지 않는다.
- 근거: 실제 실행 함수의 격리 transport/tab/native ACK 유실 회귀 포함 전체97PASS·소스 구문/권한 검사 PASS. 기존 등록 manager preview/Ensure 뒤 두 대상 worker의 fingerprint/수리코드 일치, 원 큐 revision·불명 기록 보존 확인. 실제 모델 응답 회수와 자연 quota 자동복귀는 이 검사로 증명하지 않는다. 개인 적용 영수증은 기존 중앙 정본에서 찾는다.

- 판정: 후보. HTTP202/RUNNING 저장 뒤 프로세스 내부 BackgroundTasks만으로 발신을 수행하면 프로세스 중단 시 실제 발신 여부를 잃을 수 있다. 202는 작업 접수이지 모델 실행·응답·저장 완료가 아니다.
- 확인 범위: 기존 서버 구조가 요청 응답 뒤의 비동기 처리에 의존한다는 source 조사다. 특정 미결 요청이 실제 발신됐는지는 이 구조만으로 판정할 수 없다.
- 새 설계: phase/attempt를 발신 전 보존하고 실제 받은 응답을 후속 가공 전에 저장해 재기동 시 조정한다. 반복·불명 요청은 새 모델 발신 대신 원래 attempt/result를 먼저 확인한다. 새 YouTube source 담당의 구현 보고이며 실제 성공은 미검증이다.
- 구분: metadata sync 예약과 전체 모델 요약 예약은 별개다. 임시 최초 후보는 뒤처진 스냅샷일 수 있으므로 현재 업무 repo를 정본으로 사용하며 과거 후보를 재적용하지 않는다.
- 갱신 조건: 현재 배포 source, 실제 attempt/phase/응답 선저장 및 중단 후 조정 근거가 생기면 판정을 다시 좁힌다. 여기서는 성공 해결카드나 서버 독립 완료로 승격하지 않는다. 근거는2026-10-17 KST 담당 보고이며 원문·파일 목록은 복제하지 않는다.
첨부 staged1/preflight0·복원 파일 `(1)`·클릭 뒤 API429·옛 turn 선택자0은 [기존 첨부·저장 읽기 사례](../../../web-gpt-driving/references/failure-solutions.md#첨부-인식-불일치와-전송-뒤-읽기429)에 연결한다. 전송 전 실패0과 클릭 후 불명/접수 조정을 구분한다. 새 코드의 검증 미실행과 수정 전 실제 전달 관측은 별도다.


## Host 역사적 open 세션의 반환 미입증 · 2026-11-09

- 판정: **조건부 소스 수리, 운영 해제 미확인**. CDP 기본 전환과 Host 8도구 노출이 성공해도 이전 Host open journal에 반환 미입증 세션이 있으면 새 작업은 `HOST_HISTORY_UNPROVEN`으로 차단된다. 원 결과 `OUTCOME_UNKNOWN`/`resultEvicted=true`는 지금 화면 점유나 보안 거절의 증거가 아니다.
- 원인/불명: 재시작 전에 생성한 임대/세션 객체는 현 프로세스에 없고, 구형 Aside 세션에는 재채택 가능한 정확한 대상/원 lease 반환 근거가 없다. 과거 작업이 왜 불명인지, 실제 자원이 정상 반환됐는지는 **UNKNOWN**이다.
- 실패한 방식/금지: 원 status 재조회는 원 기록만 돌려주며 원자원 반환을 증명하지 않는다. 시간 경과·프로세스 부재·과거 drain=0·새 open 요청·무소유 대상 종료·journal 수정으로 HOLD를 해제하지 않는다. 기존 절차를 반복해 복구 성공으로 보고하지 않는다.
- 최소 수리: 원 owner/세대/target/원 lease와 실제 tagged normal-close 성공 journal이 모두 맞을 때만 기존 `aicc_host_close`의 선택적 reconciliation이 원장을 그대로 보존하고 별도 SHA 결속 영수증을 만든다. 결과가 없는 원작업은 그대로 HOLD. 소스와 정확/오류 합성 검사는 `components/host-control/server.mjs`, `test/host-control-history.test.mjs`, 상세 계약은 [Host README](../../../../../components/host-control/README.md#g1-host-history--exact-normal-return-reconciliation-source-2026-11-09)에 둔다.
- 근거/해제 조건: 2026-11-09 G1 소스와 fake journal 검사. **설치0, 실제 해당 원 요청 반환증거0, 실사용 검증0**. 중앙은 새 source/pin과 바뀐 8도구 schema를 정식 후보로 별도 인수하고, 원 요청 자원의 실제 생성/정상반환이 공식 지원 자료로 증명될 때만 개별 해제를 검토한다. 다른 그룹·원 UNKNOWN은 보존한다.
