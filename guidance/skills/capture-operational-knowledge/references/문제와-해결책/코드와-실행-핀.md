## dirty와 기존 지원 도구의 일반업무

- 2026-11-11 Windows registered CDP 시작 반례: 확장 manager가 trusted Git root의 전체 dirty를 거절했고 상위 시작기는 실제 이유를 일반 실행 실패로 숨겼다. 단순 listener 부재와 확장 출처 검사를 구분한다. 시작기와 manager는 제한된 오류 코드·실패 단계·extension key만 반환하도록 수리했다. 원시 Git 오류·개인 경로는 반환하지 않는다. 실제 pin 검사와 미완료 원본은 유지한다. 4개 launcher 회귀 PASS 및 설치 manager 경로의 preview 거절 전달을 확인했다. 이는 브라우저 복구나 확장 설치 완료가 아니다. 정상 마감은 원 변경의 검토·정식 업데이트 절차에서 하며 무조건 재신뢰·dirty 삭제·다른 시작기로 우회하지 않는다.
- 같은 날 복구 인수: 기존 작성자가 반환한 큐 변경과 검증 산출물 SHA를 대조하고 코드 검토·관련 19검사를 통과했다. 로컬 runtime/원본 보존 폴더만 정확한 ignore에 포함해 보존하고, 검토한 코드만 로컬 커밋으로 확정했다. 기존 RefreshTrustRoot의 같은 origin/새 HEAD preview→apply 후 등록 시작기의 preview와 실제 시작/확장 확인이 성공했다. 원 작업 폴더·로그인·native 설치·원장은 보존했다. 단순 Git 변경 폐기나 신뢰 검사 완화로 복구하지 않는다. 확장 브라우저 복구는 native 새 기능 설치나 원 GPT의 종결·자동 quota 복귀와 별개다.

- 판정: 채택은 실행 목적의 구분이며 dirty 파일의 안전성 보장이 아니다.
- 증상/원인: 승인된 독립 연구에 기존 제출기를 쓰려다 private repo dirty만으로 미변경 불변 release를 새 gate로 요구했다. 이번 회차 제출기/의존 수정0인데 일반업무를 사후 코드 검증으로 잘못 분류한 과잉 조건이었다.
- 대안/선택: 원본 reset·깨끗한 사본 제작·재설치는 기존 작업을 훼손하거나 불필요한 실행본을 만든다. 기존 변경을 보존하고 지원 인자·route·신원·소유 target·단일 intent를 확인해 일반업무를 실행한다. 실제 기존 핀 계약을 무조건 재신뢰하거나 이번에 바꾼 코드를 검증 실행하는 뜻은 아니다.
- 근거/한계: 2026-10-17 KST 기존 도구 실제 실행은 target_attach에서 HOLD, 전송0이었다. dirty-only gate를 수정했지만 탭 연결을 해결한 성공 사례가 아니다. 현재 오류와 다음 owner는 프로젝트 정본에 둔다.
## 의존성 형태·정식 후보와 결과 인수의 누락

- 2026-11-11 실제 queue issuer URL 반례: 정상 저장 대화의 신원·주소가 일치해도 `HOLD_QUEUE_SAVED_CONVERSATION_UNPROVEN`이었다. PowerShell의 typed string 인수 `$Url`과 지역 `$url`이 같은 변수여서 TryCreate의 Uri 결과가 문자열로 강제 변환된 것이 확인 원인이다. parsed Uri는 별도 이름에 보존한다. URL의 중복 nonce 검사도 구분자를 소비하지 않는 lookahead로 고쳐 인접 중복을 거절한다. 실제 AST 블록을 typed 인수 환경에서 실행하는 회귀 8건(수리 전 정상 사례 실패), 기존 완료 target 12건, owner 준비기 7건이 통과했고 실제 두 계정의 issuer 준비 영수증도 받았다. 원 UNKNOWN 재발신과 운영 설치는 하지 않았다. 원본 증거·pin·권한은 유지하며 준비 영수증을 Chat 큐 실행 성공으로 확대하지 않는다.

- 2026-11-11 실제 Chrome target ID 반례: 등록 issuer는 대문자 hex ID를 그대로 발급했지만 owner 준비기와 Workspace 큐 제공자가 소문자만 허용해 실제 증거를 소비하지 못했다. target ID에는 대소문자 hex를 허용하고 원 proof/target 비교는 exact로 유지한다. lease token·nonce의 소문자 계약이나 소유권 검사는 넓히지 않는다. 대문자 원증거 수용, proof의 case 변경 거절, 대문자 lease token 거절 회귀 2건과 영향 21건, 실제 C# 임시 원장 연동 2건이 통과했다. 현재 설치 후보의 source pin도 갱신해야 하며 소스 수리만으로 운영 큐 성공을 주장하지 않는다. 개인 실행 대상과 미결 설치는 프로젝트 정본에 둔다.

- 관측/범위: 2026-11-08~09 Windows Host CDP 후보에서 npm/pnpm HardLink, full Playwright만 가정한 패키지 식별, 신원 감사 모듈의 UI/TS 전이 import가 순서대로 드러났다. 같은 원인 하나로 합치지 않는다.
- 수리 근거: 기존 준비기/설치기가 원본을 보존하며 일반 파일의 불변 의존성 closure와 SHA·출처·상대 import·복구를 검증하도록 변경됐다. 공식 playwright-core 단독과 일치하는 full+core만 허용하고 링크/패키지 바꿔치기/누락·변조는 계속 거절한다. private 신원 표현식은 부수효과 없는 공통 모듈로 분리해 기존 감사기도 재사용한다.
- 완료 경계: 담당의 28건 의존성 검사와 후속 core-only 26건·관련 기존2건 검사는 소스 근거다. 실제 운영 CDP 기본값·Aside 종료·RAM 절감은 별도의 설치/READY/drain/실사용 근거가 필요하다. 파일 이름만 보고 이전 후보를 재사용하지 않는다.
- 재발 방지: 읽은 결과의 실제 source/preimage SHA와 writer 반환을 기존 PROJECT/실행 원장에 함께 반영한다. 중단 뒤에는 이 영수증부터 회수하고 동일 수리를 재배정하지 않는다. 설치 입력의 패키지 종류/버전/전체 import/backup을 사전에 대조하고 새로 확인된 일반 오류만 수정한다. 보호 거절과 불명 결과를 새 후보/계정으로 우회하지 않는다.
- 갱신 조건: 설치 세대나 소스가 바뀌면 영향 범위만 재검사한다. 과거 통과는 현재 설치·실사용 성공을 뜻하지 않는다. 개인 경로·계정·현재 미결은 프로젝트 정본에만 둔다.

## 설치 준비 뒤 임시 자식 종료와 소비된 drain

- 2026-11-11 큐 임시 target 수명 반례: 배포 준비와 원격 백업 사이에 탭을 정상 반환하면 예전 live proof는 설치 권한으로 재사용할 수 없다. 같은 작업의 새 target 준비는 원 private 요청/준비 영수증을 보존하고, 계정·workspace·대화·역할·본문 불변 및 원 native run의 명시 NOT_FOUND를 검사하는 전용 rebind로 처리했다. 전후 native 조회만 사용하며 존재/불명/동시등록은 HOLD, 등록·활성화·취소를 자동 실행하지 않는다. 근접14PASS(skip0, 실제 격리 C# 포함)와 실제 두 계정 issuer의 rebind·동일 target refresh 성공/발신0 후 소유 탭2개 반환이 근거다. 이후 전체6805파일 후보 검증 도중 120초 proof 만료로 운영쓰기 전 거절됐다. 긴 검증과 현재 소유권 재확인을 분리하는 배포 계약은 미완료이며 timestamp 연장/guard 삭제로 해결하지 않는다. 후속 준비기의 verify-current-only는 원 request·역사 SHA·native pins와 현재 두 issuer 관측을 검증하고 원파일/새세대/실행승인을 쓰지 않는다. 느린 검증 후 현재 관측·상실/foreign/stale/unknown 거절을 포함한16PASS(skip0·실제격리 native포함)가 근거이며 updater/runtime가 소비하도록 연결되기 전에는 배포 freshness를 대신하지 못한다. 새 후보·양쪽 백업·정식 Apply·일반Chat 전달은 별도다.
