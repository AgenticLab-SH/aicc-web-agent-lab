# 모바일 Slack 결과 보고

사용자가 보고를 요청하면 상사에게 보고하듯 결론과 실제 결과부터 쓴다.
이번 사용자 요청의 길이 제한을 우선하고, 정기 100자 제한을 별도 상세 보고에
기계적으로 적용하지 않는다. 즉시 발송 요청은 urgency 4, 보통 보고는 2다.
예약을 꺼둔 상태라면 보고 때문에 관제 예약을 켜지 않는다.

항상 모바일 가독성을 지키고 기본 보고는 약 700자 이내로 쓴다. 사용자가 요청한 상세 범위·길이를 우선하며, 긴 UUID·경로·검사 개수 대신 실제 반영과 남은 일을 쓴다.

## 구성

1. 첫 문장: 전체 결론, 완료·미완료 범위, 사용자 조치 유무.
2. 기준 시각(KST). 과거 결과 파일 기준이면 그 시각과 현재 조회를 구별한다.
3. 그룹마다 1~2줄의 짧은 글머리표를 기본으로 쓴다. 비교가 더 쉬울 때만 2~3열의 짧은 표를 쓴다. 번호·상태만 표에 두고 긴 설명은 표 아래에 쓴다.
   모바일 가로폭을 위해 고정폭 표는 한 줄 약 32표시칸 이내로 유지한다.
   한글은 대략 2칸이다. 일반 Markdown 파이프 표를 그대로 보내지 않는다.
   기존 text 전송기는 삼중 백틱 표를 사용한다. 정식 Block Kit table 전송을
   지원하는 경로가 있으면 그 경로도 가능하되 본문 fallback을 제공한다.
4. 각 그룹: `반영:` 실제 적용된 결과 / `남음:` 미완료와 구체 원인.
5. 마지막: 다음 담당·작업, 필요한 사용자 조치. 원인 미확정은 미확정이라고 쓴다.

예시:

```text
결론: 활성 5그룹은 부분 완료, 4그룹은 대기입니다. 운영 전환 2건이 남았습니다.
기준: 11/04 14:00 KST · 각 그룹 최종 결과 기준
그룹  적용     남은 범위
G1    일부     HOME 전환
G2    일부     실제 로그인
G3    격리     운영·폰
```

상세는 그룹별 짧은 문단으로 잇는다. 접수·도구착수·소스작성·격리설치·운영적용·
실사용을 따로 판정한다. 테스트 개수나 소스 완료로 전체 완료율을 만들지 않는다.
worker가 멈췄으면 `개발 중`이라 하지 않고 `마지막 결과 부분 완료·현재 대기`라고 쓴다.
UUID·개인 경로·인증값·이메일 전체·긴 원시 로그는 본문에서 뺀다.

## 기존 봇과 명령

실제 route는 `aicc notify status --verify --json`과 owner-local 설정으로 확인한다.
AICC 운영 봇은 계정 한도·개발 결과·사용자 확인 알림을 맡고, SKCT 봇은 서비스
알림을 맡는다. 이전 이름의 DM이 남았다는 이유로 새 봇을 만들거나 삭제하지 않는다.
운영 봇 DM의 `도움말`/`메뉴`/`명령어`/`help`/`?`는 지원 기능을,
`한도`/`ocx 한도`는 계정 표를 조회한다. 일반 DM 명령이며 슬래시 명령이 아니다.
그룹 보고와 개발 지시는 기존 Codex 대화에서 요청한다. 임의 DM을 모델 실행이나
승인으로 해석하지 않는다. 설치 전에는 새 명령을 이미 작동한다고 보고하지 않는다.

## 상세 보고 발신

`scripts/send-mobile-report.mjs --input <owner-local JSON file>`를 실행한다.
설치본은 기존 스킬 배포 manifest의 AICC 정본 경로를 자동 사용한다.
입력은 기존 eventId, taskId, projectKey, title, body, urgency(2/3/4), 선택
maxChars(최대 2900)다. type은 report_ready, sensitivity는 internal로 고정된다.
검증된 기존 봇과 기존 durable outbox를 쓰고 원래 report type/정책을 유지한다.
민감·제한·OTP 알림은 이 도구가 아니라 기존 안전 renderer를 쓴다.
발신 불명은 원 outbox 영수증을 조회하며 새 ID로 재송하지 않는다.
`sent`는 API 발송이지 폰 푸시나 실제 모바일 화면 인수가 아니다.

형식 근거: https://docs.slack.dev/messaging/formatting-message-text/
및 https://docs.slack.dev/reference/block-kit/blocks/table-block/

검증과 발송은 같은 발송 동작 안에서 인증값을 한 번 읽고 그 값으로 신원 검증·전송한다. 인증값은 파일에 남기거나 다음 발송에 캐시하지 않는다. 원 report_ready/internal이 발송 전 slack_bot_token_unavailable로만 HOLD된 경우 수리 후 명시적 recoverCredentialReadFailure 입력으로 같은 event/body/CAS를 한 번 복구할 수 있다. 네트워크 불명·신원 불일치·발송됨·재복구는 거절하며 새 event ID로 재송하지 않는다.
