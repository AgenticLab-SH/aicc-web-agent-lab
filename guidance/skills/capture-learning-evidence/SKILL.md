# 학습 근거 판단

핵심은 파일 수집이 아니라 의미 판단과 자연스러운 서술이다.

## 1. 근거 읽기

1. 공식 요구사항과 원본 자료를 확인한다.
2. 현재 코드, 데이터, 설정과 재현 가능한 실행 결과를 확인한다.
3. 테스트, 로그, 수치, 스크린샷과 렌더를 관찰 근거로 연결한다.
4. 당시의 사용자 질문, 예상과 결정 기록을 읽는다.
5. AI 설명과 사후 회상은 위 근거를 보완할 때만 사용한다.

충돌하면 높은 신뢰도의 최신 근거를 우선하되 불일치를 숨기지 않는다. 자세한 판정은 [근거 게이트](references/evidence-gates.md)를 읽는다.

## 2. 학습 판정

다음 중 하나가 실제로 생겼을 때 기록한다.

- 몰랐던 질문을 조사하거나 실행해 이해가 달라졌다.
- 예상, 오류, 수정과 재검증 결과가 연결됐다.
- 선택한 설계, 대안과 이유가 남았다.
- 다른 상황에 적용할 수 있는 판단 기준을 자기 말로 설명할 수 있다.

학습 기록은 `질문 -> 탐색·시도 -> 예상 -> 관찰 결과 -> 바뀐 이해 -> 적용`의 인과가 드러나게 쓴다. 모든 항목을 같은 길이로 채우거나 자료 요약을 배움으로 과장하지 않는다.

## 3. 포트폴리오 판정

다음을 모두 확인할 때만 포트폴리오 후보로 승격한다.

1. 실제 문제가 분명하다.
2. 사용자 본인의 역할과 범위가 분명하다.
3. 대안 중 선택한 이유가 있다.
4. 테스트, 실행 또는 사용자 확인 같은 독립 증거가 있다.
5. 결과와 남은 한계를 함께 설명할 수 있다.

팀 결과와 본인 기여, 예상과 관찰, 성공과 한계를 분리한다. 외부 제출 또는 공개 사실은 실제 증거가 있을 때만 쓴다.

## 4. 대상 저장소에 기록

가장 가까운 저장소 지침, 기존 문서 구조, 상태값과 validator를 따른다. 기존 주제 문서가 있으면 자연스럽게 갱신하고 목적이 다를 때만 새 문서를 만든다. 의미 판정은 LLM이 직접 수행하고, 스크립트에는 링크·schema·상태처럼 결정적인 검사만 맡긴다.

일반 지식 볼트의 구조·출처 갱신이 목적이면 `maintain-llm-wiki`를 사용한다. 장기·multi-writer 개발의 checkpoint와 검증 사슬이 필요하면 `run-evidence-gated-ai-development`를 함께 적용한다.

## 5. 최종 검토

- 사용자가 쓴 질문과 표현의 목소리를 보존했는가?
- 명령, 파라미터, 수치, 오류와 그림이 실제 근거와 연결되는가?
- 이전 생각과 달라진 판단을 구체적으로 설명했는가?
- 수치의 단위, 조건과 비교 기준을 설명할 수 있는가?
- 근거가 부족한 항목을 `UNKNOWN`, 재현 필요 또는 검토 대기로 남겼는가?
- 저장소의 인덱스와 validator를 함께 갱신했는가?
