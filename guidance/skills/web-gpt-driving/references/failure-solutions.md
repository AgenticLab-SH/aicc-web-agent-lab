# 실패에서 남긴 복구 기준

2026-10-16 중앙 관제의 운영 기록과 코드 회귀시험에서 추출했다. 증상·원인·성공 조건을 분리하며 다른 계정이나 새 세션을 만드는 근거로 사용하지 않는다. 실제 대상과 원본 영수증은 해당 작업의 정본에만 둔다.

## 특정 탭만 시간 초과

- 증상: 탭 목록은 조회되지만 특정 탭의 focus emulation 또는 frame tree가 반복 시간 초과한다.
- 원인: 내부 원인은 미확정이다. 전체 확장 고장·로그아웃으로 단정하지 않는다.
- 해결 관측: 같은 브라우저 연결·계정의 새 소유 탭에서 같은 정확한 대화 URL을 열어 DOM으로 현재 상태와 완료 답변을 회수했다. 원래 요청 재전송과 계정·프로필 전환은 없었다. 스크린샷 복구까지 성공한 것은 아니다.
- 재시험 반례: 다른 기존 대화의 같은 URL을 같은 Chrome 새 소유 탭으로 열었을 때는 ‘이 ChatGPT 대화를 불러올 수 없습니다’와 다시 시도가 나타났다. 새 탭 회수는 조건부 시도이며 보장된 해결책이나 내부 원인 수정으로 승격하지 않는다. 이 경우 FAIL_READBACK/HOLD로 끝내고 같은 방법 반복·새 대화 생성·원요청 재전송은 하지 않는다.
- 최소 절차: 원래 전송 intent 보존 → 기존 탭의 제어 실패 범위 기록 → 새 소유 탭 사용이 허용될 때만 같은 URL의 읽기 회수 → exact 메시지 ID로 기존 응답과 결속. 다른 발신자와 동시에 조작하지 않는다.
- 금지: 새 탭에서 원래 요청 재제출, 다른 계정으로 전환, DOM 회수 성공을 확장 수리 완료로 보고.

## 초기 DOM이 아직 비어 있음

- 증상: 초기에는 pending input과 비활성 보내기만 있고 이후 대화 영역과 본문이 나타난다.
- 원인: 해당 관측만으로는 로딩 지연과 다른 내부 원인을 구분할 수 없다.
- 성공 조건: 같은 URL과 현재 메시지 ID에서 대화 영역·응답 상태를 다시 읽을 수 있음.
- 최소 절차: 준비 중 상태로 기록하고 제한된 다음 관측을 기다린다. 초안과 전송 intent를 유지한다. 빈 초기 DOM을 대화 없음·미전송 증거로 삼지 않는다.

## 불러오기 실패 뒤 일부 결과 회수

연결 해제·저장 응답 불러오기 실패가 보여도 이후 진행 또는 완료 결과가 회수될 수 있다. 타이머는 대화 URL만이 아니라 user/assistant 메시지 ID와 최초 관측 시각에 결속한다. 새 응답이나 정상 진행이면 기존 장애 시계를 초기화한다. 같은 오류 문구만으로 모든 외부 작업 실패를 선언하거나 원래 요청을 재전송하지 않는다.

## 정상 생성 대기와 완료 후 후속 한 번

별도 실제 복구에서 누적 20분 시점에 연결 끊김이 빨간 시간 초과·입력 가능으로 바뀌었다. 행동 직전 재분류해 Stop을 누르지 않고 기존 결과와 intent를 보존한 뒤 `이어서 작업해.` 한 번으로 새 user turn과 생성 재개를 관측했다. 이 결과는 재개 PASS이며 내부 원인 해결이나 맡긴 작업 완료는 미확인이다. 현재 상태를 확인하지 않고 지난 타이머만으로 중지하지 않는다.

중앙 운영에서 정상 Stop 상태를 중단하지 않고 기다린 뒤 이미지 산출 완료·입력 가능 전이를 관측했고, 후속 지시 한 번의 user turn과 응답 시작을 회수했다. 성공 조건은 완료 전이와 실제 새 turn이며 단순 버튼 클릭 영수증이 아니다. 진행 중 요청을 시험용으로 중지하거나 같은 후속 지시를 반복하지 않는다.

## 한도 배너와 이번 요청 거절

사용자가 이 환경의 workspace 한도 안내는 Codex 사용량 관련이며 무시해도 된다고 정정했다. 기존 OCX가 계정 전환과 소진 전 차단을 맡으므로 배너만 보고 일반 Chat 작업을 멈추거나 한도 회복을 기다리지 않는다. 실제 quota 거절·OCX 차단·MCP 429는 해당 요청의 근거로 별도 처리한다. [공통 운영 기준](../../manage-chatgpt-skills/references/quota-and-connection.md)을 따른다.

## 스킬 ZIP을 읽지 못한 코드 결함

기존 공용 스킬 manager는 ZIP 확장자를 허용하지만 frontmatter를 SKILL.md 파일에서만 읽어 ZIP 이름 추출이 불가능했다. ZIP 내부의 유일한 SKILL.md를 읽도록 수정했다. 참조파일을 포함한 ZIP, 복수·누락 본문, 경로 탈출, 손상 ZIP·잘못된 UTF-8·크기 제한의 회귀시험 4개를 통과했다. 이 결함을 수정한 사실은 과거 원격 ‘파일 불러오기 실패’의 원인 확정이나 원격 설치 성공을 뜻하지 않는다.

당시 업로드 전 조회는 등록 CDP offline에서 멈췄다. 현재는 상시 승인된 기존 등록 launcher·프로필 자동 기동으로 준비한다. 새 프로필·계정 전환으로 우회하지 않으며 기동 실패·신원 불일치는 해당 단계만 HOLD한다. UI의 동명 행만으로 기존 버전 일치를 선언하지 않고 HOLD_EXISTING_UNKNOWN_VERSION을 남긴다. 기존 원본과 불명 업로드를 다시 보내지 않는다.

## 답변을 못 읽어도 기존 산출물부터 회수

제작 답변을 읽지 못한 사례에서 기존 Web 실행 환경의 PDF를 재생성하지 않고 회수했다. 해당 작업자는 기존 파일 경로부터 존재 여부·페이지 수·추출 본문·해시를 대조한 뒤 같은 최종 링크를 다시 제공했다고 보고했다. 중앙이 직접 확인한 것은 최종 답변 본문과 링크의 존재이며 파일 다운로드·해시 독립 대조는 미실행이었다. 내부 장애 원인이나 상세 반복 로그는 미확정이다.

따라서 결과 회수는 기존 산출 경로·파일·기존 링크 확인을 먼저 한다. 권한 있는 동일 실행 환경의 파일 확인과 다른 주체의 본문·링크 관측, 실제 다운로드·내용 대조를 별도 증거로 남긴다. 출력 링크만으로 파일 검증 완료라 하지 않으며 원본을 덮거나 같은 결과를 재생성하지 않는다. 전용 로컬 경로를 찾지 못하면 임의의 다른 root나 공용 스킬을 수정하지 않고 원래 소유자에게 재개 조건을 남긴다.

## 산출 완료 뒤 정본과 반영 상태 대조

이미지나 PDF의 생성 완료는 최신 원장과 내용이 일치하거나 목적 문서에 삽입된 증거가 아니다. 기준일·정본 출처·확정값과 추정값을 먼저 대조하고, 구형 스냅샷이 최신 계획을 덮어 표현한 부분만 교정한다. 원장은 보존하고 산출물 교정·최종 확정·목적 문서 반영을 별도 상태로 기록한다.

완료·입력 가능·빈 composer에서 답변 불러오기 오류가 남았던 사례는 원래 intent 보존 뒤 기존 탭을 한 번 새로고침하고, 초기 빈본문을 로딩으로 분류해 다음 관측에서 최종 텍스트를 회수했다. 원요청 재전송은 없었다. 특정 실패 탭의 이미 실패한 새탭 회수를 반복하는 근거로 사용하지 않는다.

문서 표의 전체 교체가 validation_error로 실패한 뒤 기존 일반표를 소단위로 수정하고 다시 읽어 성공했다는 작업자 보고가 있다. 다음 편집은 원표를 보존하고 지원되는 정확한 셀·행 범위만 변경한다. 참조표 제한이라는 설명은 추정 원인이며 공식 제한이나 모든 표의 해결책으로 단정하지 않는다. 작업자 보고·중앙 문서 조회·산출 파일 직접 확인을 구분한다.

## Notion 첨부의 정규 참조와 원본 보존

관측된 작업자 경로는 `files.manage_library → files.read → notion_create_attachment → notion_update_page(insert_content) → notion_fetch`다. 업로드 뒤 `notion_fetch`는 원래 입력한 upload ID나 `<image>` 대신 `![](notion-file-block://...)`와 파일명을 반환할 수 있다. 정규화된 이미지 참조와 파일명을 대조하고, 원래 태그·ID가 없다는 이유만으로 실패 처리하거나 재업로드하지 않는다.

작업자는 10개 페이지에 SVG 첨부를 반영했다고 보고했다. 중앙이 직접 확인한 범위는 메인 1개 페이지의 Markdown 이미지 1개다. PNG 바이너리 직접 업로드와 모바일 앱 표시는 미확인이다. 작업자 보고를 전체 페이지의 독립 확인으로 바꾸지 않는다.

복잡한 금액·표·문자를 imagegen으로 만들면서 수치 오류가 발생했다. 작업자는 최신 정본 조회 → 수치·수식 대조 → 개별 SVG 제작 → PNG 내보내기로 대응했다고 보고했다. 이는 후보 절차이며 원인 설명은 추정이다. 변환 명령 로그와 전체 바이너리를 독립 확인하지 않았으므로 일반적인 해결 완료로 선언하지 않는다. 실제 금액·문서 원문은 해당 작업 정본에만 둔다.

기존 DB 참조 보존은 실패 복구가 아니라 정상 편집 절차다. 기존 참조를 먼저 조회하고 `replace_content` 대신 `insert_content`로 이미지 구역을 추가한 뒤, 새 이미지와 기존 DB·하위 페이지 참조를 함께 대조한다. 참조가 남은 사실만으로 DB 관계와 수식 내부까지 시험했다고 보고하지 않는다.
## 목록 로딩과 페이지 전환의 실제 완료

관리자 스킬 화면은 처음에 머리글만 보이다가 항목과 3페이지 표시를 반환했다. 페이지 번호가 먼저 바뀌고 항목은 이전 페이지에 남아 있을 수 있다. 최초 빈 화면이나 첫 페이지의 이름 부재를 전체 부재로 처리하지 않는다. 등록된 소유 탭 안에서 페이지 버튼을 화면 안으로 스크롤하고, 번호와 항목 집합의 전이가 모두 끝날 때까지 기다린 뒤 전체 페이지의 exact 이름을 모은다. 이 보완 뒤 실제 3페이지·54개 항목 회수가 관측됐다. 화면 밖 좌표와 렌더링 지연이라는 설명을 모든 페이지 장애의 확정 원인으로 확대하지 않는다.

같은 작업에서 별도 Playwright 연결은 WebSocket handshake에 실패했고 이후 등록 Chrome의 endpoint와 프로세스가 사라졌다. 종료 원인은 미확정이다. 사용자 재시도 지시 후 같은 등록 프로필로 연결을 복구하고, 이전 불명 lease의 정확한 소유 대상부터 공식 반환해 정리했다. 로그인 초기화·다른 계정·프로필 전환은 없었다. 이 결과를 미래 연결의 영구 보장으로 쓰지 않는다.

## 입력 도구의 시간 초과와 실제 접수 조정

중앙은 기존 탭이 사라진 상태에서 사용자 재시도 범위 안의 정확한 기존 대화 URL을 다시 열고, 초기 로딩 뒤 Notion 최종 답변과 유튜브 배포 결과 본문을 회수했다고 보고했다. 새 탭 자체가 근본 해결이라는 뜻은 아니다. 로딩 대기와 최종 읽기 실패를 구분한다.

중앙의 유튜브 후속 입력에서 Enter 도구는 CDP key timeout을 반환했지만, 같은 대화의 재관측에는 새 user turn과 중지 버튼이 있었다. 도구 오류를 미접수로 단정하지 않고 실제 접수로 조정해 재전송하지 않았다. 이 접수 증거를 맡긴 작업의 완료로 확대하지 않는다. 진행 중인 대화에 다른 발신자가 추가 지시를 보내지 않는다.
## 스킬 업로드의 불명 응답과 원격 ID 조정

관리자 업로드 뒤 응답 관측 또는 완료 화면 대기가 시간 초과했지만 실제 스킬은 생성돼 있었다. 이전 manager의 skill 문자열 응답 필터는 실제 hazelnuts/uploads/create 경로를 놓쳤고, 필터 보완 뒤에도 완료 화면은 관측하지 못했다. 두 신규 스킬은 재전송 없이 기존 owner 목록과 editor에서 불변 ID·slug·정본의 논리 본문 일치를 회수했다. 완료 화면 시간 초과의 내부 원인은 미확정이다.

표시명은 업로드 slug와 다르게 비동기로 바뀔 수 있다. 전송 전 계정·workspace·이름에 결속한 영속 기록을 만들고 HTTP 응답은 후속 UI 읽기 전에 보존한다. 불명 결과는 기존 remote ID와 본문을 읽어 조정하며 원래 HTTP ACK를 사후 성공으로 꾸미지 않는다. 본문 일치와 ZIP 참조 전체·다른 계정의 가시성·실제 스킬 호출은 별도다.
## 탭 목록 성공과 제어 초기화 실패를 분리

확장 소스의 관측 경로는 attach → focus emulation → attached 상태 등록이다. focus 명령의 시간 초과가 등록 전에 나면 목록 조회·handoff 성공과 특정 탭의 Debugger unattached가 함께 발생할 수 있다. 이 순서 대조는 실패 단계를 좁힌 근거이며 Chrome 내부 원인·다른 debugger 충돌의 확정 증거가 아니다. detach 이유가 기록되지 않은 코드에서는 이유를 추측해 채우지 않는다.

후속 중앙 보고에서는 같은 브라우저의 기존 두 탭 읽기가 재개됐고 다른 한 탭의 focus 시간 초과는 남았다. 탭마다 현재 상태를 대조하며 전체 확장 복구나 전체 한도 차단으로 일반화하지 않는다. 등록 CDP 프로세스와 일반 Chrome의 확장 호스트는 다를 수 있으므로 포트나 browser 번호만으로 동일 프로필이라 하지 않는다. 브라우저 종료·계정 전환·공급자 도구 패치는 이 진단의 자동 후속 행동이 아니다.

## 기존 프로필 잠금과 실제 로그인 화면

중앙이 회수한 작업자 보고에서 owner_browser_busy는 기존 정상 프로필의 독점 잠금으로 재분류됐고, 서비스 비로그인은 실제 화면으로 판정했다. 이는 후보 운영 절차다. 잠금만으로 고장·로그아웃이라 하지 않고 현재 소유자와 실제 로그인 화면, 기존 설정을 대조한다. 기존 릴리스·인증·프로필을 보존하며 잠금을 강제로 풀거나 다른 계정으로 우회하지 않는다. DNS·TLS·익명 요청의 로그인 리다이렉트 성공과 로그인 후 원본 서비스 접속 성공도 별도로 남긴다.

## 프로젝트 생성 응답 뒤 불변 ID 회수

생성 버튼의 접수 후 옛 메뉴 locator가 실패해도 생성 전체 실패로 처리하지 않는다. 기존 identity-bound 목록에서 같은 이름의 유일한 불변 ID를 회수한 뒤 그 프로젝트의 지침·자료·고정을 각각 이어간다. 생성 전 입력 locator 실패와 생성 후 설정 실패를 구분하고, 전송 뒤 결과가 불명이면 프로젝트를 다시 만들지 않는다. 이번 사례는 원격 ID 회수 후 지침과 자료 등록, 고정 표시를 확인했으며 자료 목록 일치를 원격 파일 바이트 일치로 확대하지 않았다.
## 새로고침 뒤 바뀐 렌더 ID

중앙은 같은 기존 대화를 새로고침해 읽기를 회수했지만 data-dil-message-id wrapper가 달라졌다고 보고했다. 이 값의 지속성은 미확인이다. 렌더 ID 변화만으로 새 user/assistant 응답 시작을 선언하거나, 이전 시각과 이어 같은 응답의 정체 시간을 확정하지 않는다. 실제 안정 message ID·원래 intent·현재 내용·생성 상태와의 대조가 필요하며, 대조가 안 된 타이머는 해당 중지 판단의 근거로 쓰지 않는다. 이는 읽기 회수 성공을 부정하거나 모든 복구를 막는 규칙이 아니다.
## 시험과 근거

- 중앙의 프로젝트 정본·메시지 ID가 결속된 운영 상태는 관측 증거다. 회수한 원문·금액·비밀·긴 로그는 이 참조에 복제하지 않는다.
- 코드 시험: private tests/chatgpt-skill-upload-package.test.mjs. 기존 요청을 다시 보내지 않는 로컬 ZIP 회귀시험이다.

## 입력 가능과 최신 답변 본문 확인을 분리

지정된 기존 두 대화의 동일 신원 읽기에서 빈 composer·중지 버튼 없음·과거 다시 생성 버튼이 함께 관측됐지만 최신 ChatGPT 답변 본문은 비어 있었다. 하나는 저장된 후속 지시와 도구 활동이, 다른 하나는 지시와 처리 시간만 보였다. 입력 가능·이전 완료 제어만으로 최신 작업 완료나 최신 답변 표시를 판정하지 않는다. 기존 intent는 접수 근거로 보존하고 본문은 미확인으로 남기며 원요청을 재전송하지 않는다. 안정 message ID 미노출과 렌더 wrapper를 구분한다.

메타데이터 classifier는 최신 assistant 본문 가시성 근거가 없으면 IDLE_RESULT_UNCONFIRMED를 반환하도록 보완했다. 이 코드 변경은 사후 검증 미실행이다. 동일 계정·workspace의 지정 읽기 회수 성공은 중앙 확장 focus 오류의 해결이나 다른 surface의 동일 프로필 증명이 아니다.
## 최종 본문 공백 뒤 목적 문서의 변경 이력 회수

중앙은 Notion 최종 답변 공백을 원요청 재전송 없이 기존 변경 이력으로 회수했다고 보고했다. 15페이지·75표 폭맞춤과 원본 백업 대사를 보고했지만 root의 독립 페이지 검사는 아니다. mailto 정규화, 공백·목록기호·복제 child/file ID 차이는 비교에서만 정규화하며 원문을 재덮는 이유로 사용하지 않는다. 실제 원문 일치, 표시 정규화에 따른 대사와 미확인 원인을 분리한다. details 변환 시각 보존과 unknown copy_indicator의 실제 화면은 미확인이었다.

해당 작업의 브라우저 읽기는 안전검사 차단 보고가 있다. 본문이 비었다는 이유로 다른 도구·계정·Work 전환으로 그 차단을 우회하지 않는다. 허용된 기존 artifact·변경 이력에서 읽은 결과와 차단되어 미실행인 실제 화면 확인을 별도로 남긴다. 후속 발신은 원래 중앙 담당자 하나만 유지한다.

## 참조 파일 트리와 저장 전 버전 충돌

기존 스킬 편집기의 보조 파일 행은 basename이 아니라 references/파일명 전체를 접근성 이름으로 노출했다. lazy tree 로딩을 기다리고 접힌 폴더만 펼친다. 참조 선택 뒤 description 입력란이 사라질 수 있어 먼저 읽은 메타데이터와 선택한 파일 본문을 구분한다. ZIP의 CRLF와 editor 논리 LF 차이로 guard가 저장 전에 거절된 사례는 무변경으로 보존했다. fresh 전체 본문을 회수해 줄바꿈 차이와 기능 차이를 대조한 뒤 새 exact SHA로 별도1회 저장했다. 해시를 임의 완화하거나 불명 저장을 재전송하는 절차가 아니다.

## 최신 답변 로딩 오류의 읽기 회수

지정 관제 대화에서 최신 assistant가 제목만 보인 뒤 ‘이 응답을 불러오지 못했습니다’ 상태를 반환했다. 기존 응답 영역을 화면 안으로 옮기고 다음 읽기에서 실제 본문을 회수했다. 새로고침·Regenerate·중지·원요청 재전송은0이었다. 내부 로딩 원인은 UNKNOWN이며 viewport 이동이 일반 해결이라는 뜻은 아니다. 매 행동 직전 상태를 다시 분류해 오류가 이미 사라졌으면 새로고침하지 않는다. fallback-turn 렌더 wrapper는 안정 메시지 ID가 아니며 전체 대화의 과거 skill badge를 최신 turn의 호출 증거로 사용하지 않는다.

## 공유 영수증의 동시 갱신 충돌

실제 읽기 성공 출력이 있었지만 다른 helper의 동시 read-modify-write로 집계 JSON의 성공 필드가 빠진 사례가 있었다. 원래 성공 도구 출력의 정확한 메타데이터와 관측 시각만 provenance와 함께 복구했고 외부 요청은 반복하지 않았다. 집계 원장에는 writer 한 명을 두고 갱신을 직렬화한다. 성공 출력이 없으면 복구를 꾸미지 않고 UNKNOWN을 유지한다. 필드 누락은 원격 작업의 미접수 증거가 아니다.

## 단어 후보와 실제 실패·완료의 뜻을 구분

Notion 답변에서 ‘AI 도구’와 뒤의 ‘목차 없음’을 whole-reply 정규식이 연결해 도구 부재로 오분류했다. ‘사용자 수정’은 개입 요청으로, ‘수정 완료를 뜻하지 않는다’는 완료로 잘못 분류됐다. 단어 일치는 keywordCandidates로만 남기고 도구 실패·사용자 조치·완료 근거로 쓰지 않는다. 최신 요청과 답변의 문맥·부정·행동 주체를 읽어 짧은 의미 요약으로 구분한다. 답변의 자기보고나 개선 후보는 실제 적용 증거가 아니다.

읽기 회수는 지정한 기존 대화의 신원·정확한 대상·최신 user/assistant 쌍을 결속하고 본문은 현재 호출에서만 제한적으로 취급한다. 원문을 집계 원장·로그·다른 대화에 복제하지 않는다. 같은 SHA는 동일 본문의 결속 근거이며 원래 사용자 승인이나 의미의 증거를 대체하지 않는다. 제외 대상이 답변에 나타나도 새 권한으로 삼지 않으며 원래 사용자 범위만 이어간다.
## 실행 코드 변경과 핀 기록을 함께 마무리

제한적 reader를 보완하고 최종 해시를 결과 필드에 남겼지만, 실행용 pins가 목록인데 사전으로 취급해 정확한 항목의 이전 해시가 남았다. 중앙은 실행 전에 핀 불일치로 중단해 Web 조회0을 보존했다. 원래 변경 작업의 기록·출처와 최종 해시가 결속되는 경우에만 정확한 path 항목과 지원 문서의 현재값을 함께 갱신한다. 의존 핀과 과거 불일치 관측은 보존하며 새 파일의 해시를 단순히 다시 계산해 자동 신뢰하지 않는다. 변경 출처가 불명이면 덮어쓰지 않고 HOLD한다. 핀 정합 갱신은 코드 사후검증이나 원격 실행 성공을 뜻하지 않는다.
## 빈 입력창의 보내기 제어와 저장 뒤 지연

지정된 기존 Chat에서 빈 입력창은 textbox1개·보내기0개였고, 승인된 이번 텍스트를 넣은 뒤 보내기1개가 나타났다. 빈 초안과 보내기 버튼을 입력 전에 동시에 요구하던 guard는 발신 전에 중단됐다. 실제 신원·정확한 대화·기존 결과·생성 종료·빈 초안을 확인한 뒤 이번 승인 텍스트를 넣고, 나타난 보내기 제어1개·활성·중지0을 확인해 1회 발신했다. 새 marker 사용자 turn 접수와 생성 재개를 관측했으며 목표 완료 증거는 아니다. 입력 뒤 실패는 준비된 초안으로, 클릭 뒤 불명은 전송불명으로 보존해 같은 요청을 다시 보내거나 사용자 초안을 지우지 않는다.

같은 운영 구간의 스킬 파일 저장에서는 버튼 클릭 직후 재조회에 이전 본문이 나타났지만, 불명 결과를 제한적으로 한 번 회수했을 때 원하는 전체 본문이 저장돼 있었다. 새 저장은0이었다. 지연의 내부 원인은 미확정이며, 즉시 옛 해시가 보였다는 이유만으로 실패를 확정해 재저장하지 않는다. 이 사례는 통과한 시험 반복이나 모든 저장의 고정 대기 시간을 정하는 근거가 아니다.
## 전달 수단 부재와 정상 생성은 한도 차단이 아니다

큐 등록·감시기 실행·OCX 풀 준비와 실제 공식 메시지 전달은 별개다. 로컬 continuity worker에는 공식 send_message_to_thread를 호출하는 호스트 계약이 없다. 별도 공식 도구 에이전트의 Queue→Claim→ACK→marker/새 turn Observe만 기존 지원 경로이며 자기 발신·내장 goal blocked 자동 해제를 하지 않는다. Status/DesktopQueue의 reason과 단계별 근거를 읽고 일반 인계 성공을 과거 Claim의 ACK로 기록하지 않는다. helper 교체 후에는 registry의 현재 핀과 필수 SenderThreadId 계약을 홈 참조에도 함께 반영한다.

실제 읽은 두 담당 대화의 Stop=1·빈 입력·경고0은 UI상 생성 중이며 실제 진척은 미확인이다. 새 응답·도구 결과·산출물 변화가 관측돼야 그 범위의 진척을 말한다. 긴 경과나 같은 본문/SHA만으로 정상 진척·끊김·한도 실패를 확정하지 않으며 시간만으로 중지할 새 규칙을 만들지 않는다. 한 번 전송한 intent는 결과만 회수하고 미전송 intent는 새 idle/신원/정확한 user-assistant 쌍/빈 초안/불명0이 맞을 때만 잔여1회를 쓴다.

모바일 후보 조립 전에 선택 overlay의 모든 소스 변경을 끝낸다. 조립 도중 소스가 바뀌어 source_changed_before_copy로 끝나면 부분 후보를 보존하고 실패한 준비로 기록한다. 원결과 불명이 아니고 도구가 명확히 중단을 보고한 경우에만 새 immutable 준비를 시작한다. 조립 성공은 공개 서비스 활성화나 폰 조작 성공이 아니다.
기존 editor 참조를 읽는 단계에서 page.evaluate timeout이 발생하면 저장 전 읽기 실패로 보존한다. 원하는 본문/preimage를 확보하지 못했으므로 저장을 시도하지 않고 다른 계정·브라우저·새 연결로 우회하지 않는다. 이 현상을 quota 한도 증거로 바꾸지 않는다. 동일 ID의 편집기/등록 세션이 정상화되어 새 preimage를 읽을 수 있을 때만 원래 문서 변경을 이어간다.

- 수정 전 직접 관측(2026-10-17 KST): 프로필 로딩 중에는 모델 제어가 없다가 뒤에 나타났다. broad selector는 Plugins도 포함했고, 트리거 전체 문자열에는 숨은 애니메이션 라벨이 함께 들어갔다. 열린 메뉴의 radio는 모델 행이어서 기존 effort index를 그대로 적용하면 다른 모델 행을 가리켰다. 초기 제어 부재·선택자 혼입·의미 오인을 구분하며 이를 로그아웃·한도·attach 실패의 공통 원인으로 합치지 않는다.
- 소스 수정안: composer 소유의 exact 명명 trigger, 명시 selectedEffort와 단일 활성 라벨의 일치, aria-controls의 정확한 popup 결속, 모델 행을 제외한 의미별 effort 필터를 사용한다. 현대 Max/Ultra를 legacy Pro로 바꾸지 않는다. 같은 계정·모델·경로를 보존하며 의미가 맞지 않으면 전송 전에 보류한다.
- 한계와 갱신: 이번의 70초 대기는 해당 구현의 로딩 예산일 뿐 일반 복구 보장이 아니다. 특정 slider/radio index도 의미나 미래 UI 계약의 증거가 아니다. 수정 뒤 실행·브라우저·테스트·빌드·검증 목적 재읽기는 미실행이며 연구 전송도 없었다. 실제 허용 동작의 새 근거가 생길 때만 그 단계를 갱신한다.
- 최소 절차: exact 실패 단계와 전송 여부를 보존 → 수정 전 UI 의미/의존 관계를 구분 → 기존 작성자가 필요한 범위만 수정 → 현재 정책이 허용한 적용 단계로 인계. 코드 수정 자체와 실제 요청 접수·응답·스킬 호출은 별도다.

## 새 소유 탭의 Work 기본값·복원 초안과 현재 effort

사용자가 명시한 브라우저 사용 확인(2026-10-17 KST)에서는 기존 등록 프로필 기동·실제 신원 읽기와 개인 스킬 관리가 성공했지만 새 root의 기본 모드는 Work였다. Chat/Work는 role=radio가 아니라 작성기 모드 group의 aria-pressed 버튼이었다. Work의 화면 placeholder와 실제 논리 텍스트를 구분하고, 빈 작성기·기존 turn0인 자기 소유 target에서만 Chat을 선택한다. Work로 전송하지 않는다. 기존 사용자·다른 task 탭의 초안은 보존한다. 새 task-owned 탭·새 대화의 복원 초안은 use-web-gpt의 새 탭 계약에 따라 정리할 수 있다.

새 소유 root에도 원래 caller의 미전송 초안이 복원될 수 있었다. 당시에는 정확한 caller 원문 hash와 논리 텍스트가 일치할 때만 초안을 회수했다. 현재 사용자 지시(2026-10-21)로 새 task-owned 탭의 새 일반 Chat·기존 turn0에서는 복원 초안을 정리할 수 있다. 기존 사용자 탭과 저장 대화를 이어가는 탭은 기존 보존 경계를 따른다. 원래 요청의 접수불명은 그대로 유지했고 원요청 재전송은0이었다. 단지 길이가 같다는 이유로 초안 소유권을 판단하지 않는다. 소스 구현과 이 제한된 명시 확인을 일반 코드 사후검증으로 확대하지 않는다.

빈 일반 Chat 준비 뒤에는 모델 의미가 별도 gate였다. 실제 trigger의 data-selected-reasoning-effort=high와 열린 메뉴의 5단계 slider를 관측했고 한 칸 오른쪽은 max였다. xhigh/Extra High와 같다고 바꾸지 않았으며 전송0으로 멈췄다. 원래 High 복원을 요청한 사실과 복원 결과를 구분한다. 다른 시점에 xhigh가 관측됐다는 과거 사례로 현재값을 대신하지 않는다. 이 불일치는 해당 요청 모델 조건의 HOLD이며 모든 스킬 관리·패키지 교체나 계정의 quota 차단을 뜻하지 않는다. 사용자의 실제 모델 선택이나 현 UI의 의미 결속이 생길 때에만 해당 전송을 재개한다.

### Windows 저장 후속 CLI의 실행기 별칭 반복 실패 · 2026-11-10

- 증상: Node의 strip-only TypeScript 오류와 Bun 실행 시 coordination_unavailable가 서로 다른 단계에서 발생했다. 전자는 packageManager 불일치, 후자는 WindowsApps PowerShell 별칭 spawn 실패로 구분한다. CDP timeout은 별도 전송/응답 상태이며 신원 거절로 바꾸지 않는다.
- 수리: 기존 Invoke-ProjectBun 진입이 정식 packageManager를 고르고 현재 PowerShell process의 실제 exe를 기존 AICC_PWSH_EXE 옵션으로 자식에 전달한다. 명시한 exe는 그대로 검사하며 부모 환경은 finally로 복원한다. 보안 거절·identity mismatch에는 대체 실행기를 쓰지 않는다.
- 근거: 같은 원 saved 요청의 정확 branch·prompt·user·최종 assistant와 렌더 완료를 실제 회수했고 Workspace closed=true 반환을 인수했다. 재전송0. saved CLI는 기존 source-import 실행 경로에 연결돼 있으며 17841 서비스는 교체하지 않았다. 과거 CLI 미구현 표기는 당시 한계다.
- 적용: 기존 Windows package launcher를 사용한다. 단회 성공은 무인 관제나 전체 브라우저 장애 해결의 증거가 아니며 실제 그룹 미결은 프로젝트 정본에 둔다.
