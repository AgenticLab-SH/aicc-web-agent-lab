# codex-web-low-token-workflow 선택 절차

이 문서에서 선택한 단계만 읽는다. 명령 예제의 기준 작업 폴더와 인라인 리소스 경로는 상위 스킬 루트다. Markdown 링크는 이 파일 위치를 기준으로 한다.

## 역할 선택

### 실행을 맡기는 기준

지피티는 기존 AICC Workspace의 실제 파일/명령/도구/스킬로 구현·적용까지 우선 맡는다. 사용자 계정1·2의 실제 신원과 workspace는 소유자 등록에서 확인하며 포트·순서로 추정하지 않는다. 원하는 작업공간은 실제 등록/grant 안에서 고른다. 서버도 제공 도구로 가능하면 문서화된 경로로 맡긴다. 코덱스는 관제와 실제 미지원·미해결·필요한 직접 로컬/화면 조작을 잇고 AI 기반을 만드는 현재 단계의 통합 수행을 맡을 수 있다.

RDC·예비 AICC는 실제 지원 범위의 예비경로다. 읽기 전용을 쓰기로 확대하지 않으며 보안 거절이나 불명 요청을 우회하지 않는다. 지피티의 CUA 시도는 현재 노출 도구로만 한다. 사용자의 Chrome/앱·입력을 보존하며 소유 탭/창/lease로 분리하고, 같은 파일/데이터/배포 효과와 물리 포커스 작업의 담당을 조정한다.

제품은 기존 진입문서에서 실제 명령/API·서버 운영·권한·저장/복구·현재 상태를 익혀 수행할 수 있도록 개발한다. 정리는 보관이 기본이며 최종 영구삭제는 사용자와 코덱스가 함께 한다. 상세 계약을 별도 스킬에 중복하지 않는다.


### 두 환경의 사용자 화면 제작 기준

코덱스와 지피티 모두 사용자 화면·시각 산출물의 글자/배경 대비를 먼저 확보한다. 조작 기능은 목적·사용 순서·실행 결과·불가 이유를 쉬운 말로 제공한다. 기본·비활성·선택·포커스·로딩 상태에서도 읽을 수 있어야 한다. 호버 설명과 키보드 포커스/접근성 설명을 연결하고 터치·클릭 도움말도 둔다. 핵심 안내와 오류는 호버에만 숨기지 않는다. 긴 설명은 스크롤 가능한 도움말에 둔다. 실제 작업 완료와 큐/화면 상태를 혼동하는 명칭을 쓰지 않는다. 세부 구현은 현재 AICC 스킬 목록에서 Windows는 windows-design, 웹 UI는 codex-frontend의 최신 본문을 읽는다. 구현·배포·시각 검증은 구분하며 검사 범위는 현재 정책과 명시 요청을 따른다.

사용자 운영 기준은 Codex의 빠른 로컬 처리와 한도 부담을 고려하고, 상대적으로 느려도 Web의 조사·판단을 충분히 활용하는 것이다. Web을 토큰당 과금 경로로 다루지 않는 선호와 제품의 실제 요금·계정 사용 한도는 구분한다. 속도·총비용·절감률을 측정 없이 수치로 만들지 않는다.

Web의 CUA 브라우저도 사용할 수 있지만 해당 방식이 화면·포커스를 점유하면 사용자 작업에 영향을 준다. 현재 제공되는 배경 Chrome·CDP·connector 경로를 우선 검토한다. 어느 제품의 도구가 독점 제공된다고 고정하지 않는다.

## 일반 작업은 OCX, 연결 교체는 독립 실행 수단

1. 별도 경로 지시가 없는 일반 Codex 작업은 준비된 **OCX 직접 경로**를 우선한다. command-route-r2의 공식 `codex`와 공유 HOME 사용자 설정을 따른다. 명시 OCX 호환 실행이 필요한 경우만 기존 `aicc codex ocx`를 사용한다. 현재 모델 catalog·health·ready·모델 노출을 확인한다. 모델과 effort는 사용자의 현재 요청을 유지한다.
2. OCX는 로컬 프록시와 서버·인증 연결에 의존한다. OCX·AICC 포트, proxy, Tunnel, 실행기나 연결 복구 경로 자체를 바꾸는 구간은 해당 연결과 무관하게 살아남는 **독립 실행·복구 수단**이 맡는다. 기존 guarded PowerShell 설치기로 준비된 변경과 복구를 수행할 수 있고 실제 독립 준비·현재 유휴·rollback 조건을 충족하면 모델 없이 실행한다. PowerShell 자체는 모델 토큰을 쓰지 않는다. 판단·구현 준비는 OCX에서 마치며, 네이티브 코덱스는 OCX·AICC 업그레이드로 OCX가 끊기는 구간의 독립 유지보수·복구에만 사용한다.
3. 네이티브 코덱스를 사용하는 경우 공식 Codex endpoint에 직접 연결하며 OCX 자동 계정풀을 거치지 않는다는 한도 차이를 먼저 설명한다. 현재 프로세스의 provider·endpoint를 확인하고 이름이나 모델명으로 경로를 추측하지 않는다. 모델 없는 PowerShell도 원래 메인 종료 뒤 실제 실행·복구할 수 있는지 확인해야 한다. 독립 경로가 준비되지 않았으면 연결을 끊는 작업을 시작하지 않는다.
4. OCX 작업에서 유지보수가 필요하면 같은 정본에 원래 thread, 맡은 목표, 끝낸 일, 남은 일과 재개 조건을 남긴다. 주 담당자가 소유한 대상의 실제 활성 턴을 확인하고 필요한 작업만 중단한다. 무관하거나 소유 불명인 대화를 강제 종료하지 않는다.
5. 독립 실행 수단에서 좁은 변경·복구를 처리하고 필요한 경우만 요청된 검사와 실제 읽기를 수행한다. 그 뒤 **원래 OCX 대화**를 재개하며 `중단된 지점부터 너의 주어진 일 달성을 위해 재개해`라고 전달한다. 전달·대기·완료는 각각 실제 영수증으로 구분한다.
6. 실패했다고 같은 대화를 새로 만들거나 다른 계정·provider로 조용히 전환하지 않는다. 일반 업무를 OCX 장애 때문에 네이티브 코덱스로 자동 배정하지 않는다. 정비 구간의 일시 사용 범위·담당·복귀 조건을 정본에 기록한다. 원래 OCX 경로의 준비 상태를 거짓 성공으로 만들지 않는다.

이 기준은 전역 설정을 즉시 교체하라는 뜻이 아니다. 기존 유지보수 대화와 영수증을 보존하고, 끝난 응답을 프로세스 종료나 live READY로 취급하지 않는다. 사용자 지시가 OCX이면 추가 AI 작업도 OCX에서 수행한다. 새 일반 작업이나 재개할 원래 작업에 해당 실행기를 적용한다. 경로 변경의 실제 절차는 `manage-codex-model-routes`와 `codex-rescue-preflight`를 따른다.

## 독립 세션과 관리기 입력

승인된 독립 코덱스는 기존 OCX·모델로 `-C <작업폴더> -a on-request -c 'approvals_reviewer="auto_review"' -s danger-full-access`를 사용하고 기존 대화는 정확 ID로 resume한다. never는 모두 허용이 아니라 승인 요청 금지다. 도구·조직 정책·명시적 보안 거절을 완화하거나 우회하지 않는다.

AICC 관리기 안의 코덱스 관리기·지피티 관리기는 관리대상을 구분한다. 실제 실행 담당과 완료 근거는 따로 남긴다. 일반 Chat의 고정 `aicc_web_management_start` 요청파일은 `{"schemaVersion":1,"action":"instructions-inspect"}`처럼 지원 action 필드만 넣고, config/account/identity/resultFile/slotPort/allowBrowserStart 같은 로컬 CLI host필드는 넣지 않는다. 등록 workspace·상대 경로·정확 파일 SHA를 사용하며 provider가 계정과 실행기를 고정한다. 상세와 기존 요청 준비기는 AICC docs/runbooks/workspace-web-management.md 및 tools/platform/chatgpt/Prepare-WebManagementRequest.ps1을 필요한 부분만 읽는다. 실패 단계·원 요청·실제 쓰기 여부를 보존하고, 일반 파일 오류를 권한 부족이나 보안 거절로 단정하지 않는다. 원 불명·명시적 거절은 재생하지 않는다.
