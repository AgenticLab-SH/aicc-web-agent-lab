# 일반적인 요청에서 서비스 장애 해결까지

“상황 파악해서 AICC로 접속해서 그 서비스 문제 해결해둬”, “주말 경기가 안 나와. 로그 보고 고쳐줘”는 맡긴 서비스의 조사와 수정을 실행하는 요청이다. 사용자가 도구 이름이나 호스트 명령을 직접 지정할 때까지 기다리지 않는다. 일반 Chat의 현재 AICC 연결을 사용하며 같은 일을 다른 AI에 다시 보내는 것을 선행 조건으로 삼지 않는다.

1. **서비스를 식별한다.** 현재 대화의 서비스명·URL과 `aicc_workspace_list`의 등록 별칭을 맞춘다. 해당 root의 README, 가까운 AGENTS.md, context/PROJECT.md에서 운영 URL·배포 대상·로그·현재 담당자를 찾는다. 별칭만 모르면 등록된 상위 작업공간의 기존 서비스 목록을 읽는다. 서로 다른 서비스가 여전히 둘 이상일 때만 짧게 묻는다. 첫 조회는 읽기 전용으로 한다.
2. **현재 장애를 좁힌다.** 운영 버전·최근 배포·실패 시각과 시간대·영향 범위를 확인하고 필요한 서버 로그, cache, DB 상태와 공급자 응답을 읽는다. 등록된 원격 운영 절차와 기존 인증을 사용한다. 로그의 사용자 원문·토큰은 출력하지 않는다. “로그 없음”을 “오류 없음”으로 해석하지 않는다.
3. **원인에 맞게 수정한다.** 코드·cache·공급자 지연·인증 문제를 구별한다. 데이터가 서버에 있는지, API가 반환하는지, 화면 필터·버튼이 숨기는지 각각 확인한다. 축구 서비스에서는 예정·진행·종료 상태, 리그·월·날짜와 일정 목록/선수 상세 제공 여부를 나눠 본다. 알 수 없는 공급자 상태나 미제공 패스를 추측해 생성하지 않는다.
4. **작성권을 확보해 실행한다.** 현재 담당자와 겹치지 않게 한 root의 writer를 하나로 두고 승인된 read-write lease로 전환한다. dirty와 수정 전 원본·해시를 보존한다. 실제 노출된 patch/exec 도구로 작은 가역 수리를 진행하고 관련 회귀 검사를 수행한다. 검사 범위는 현재 적용 정책과 사용자 요청을 따른다. 실행 session은 같은 ID로 회수하고 불명 변경을 재생하지 않는다.
5. **정식 적용과 운영 확인까지 잇는다.** README의 기존 설치·배포 경로와 복구점을 사용한다. 서비스 중단이 필요하면 영향·예상 시간·복구 방법을 먼저 알린다. 새 공개·결제·계정/권한 변경·복구 어려운 삭제는 기존 승인 범위를 넘기지 않는다. 실제 보안 거절은 정확한 동작과 이유를 남기며 다른 경로로 우회하지 않는다. 제공 도구로 불가능한 단계만 부분 결과와 함께 담당자에게 넘긴다.
6. **실제로 달라진 것을 보고한다.** 원인·변경 파일·검사·설치/배포 버전·원래 증상의 운영 확인·남은 조건·복구점을 구분한다. 테스트 통과를 운영 해결로 올리지 않는다. 완료 또는 인계 시 workspace를 닫고 작성권을 반환한다. 후속 일이 있는 저장 대화는 재사용하고, 역할이 끝난 소유 탭만 기존 탭 관리 절차로 정리한다.

도구 목록·연결 표시·큐 접수는 실제 수리 증거가 아니다. 최소 인수 근거는 해당 서비스의 실제 파일/명령 결과와 원 증상이 해소된 운영 응답 또는 화면이다. 문서 개선만 했으면 절차 준비로, 소스만 고쳤으면 적용 전으로 보고한다.

## 인증·브라우저에서 너무 일찍 멈추지 않기

CUA/확장 host, 등록 CDP, 서비스 로그인, GitHub CLI keyring과 Git helper를 별개로 판단한다. 브라우저 검증은 `browser-qa`, 기존 로그인의 재사용은 `complete-site-login`, Git 세션 차이는 `release-git-cloudflare`의 인증 절차를 따른다. 서비스 점검에 필요한 기존 계정 선택·일반 로그인은 사용자 작업 범위에서 진행한다. 프롬프트 작성자가 스스로 붙인 로그인 금지를 사용자 금지로 오인하지 않는다. 실제 보안 거절·새 grant·사용자의 명시 금지는 계속 지킨다. '접근 불가' 보고에는 실패한 정확한 경로와 확인한 기존 지원 경로를 함께 남긴다.
