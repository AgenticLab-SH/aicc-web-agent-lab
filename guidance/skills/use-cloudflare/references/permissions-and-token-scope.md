# use-cloudflare 선택 절차

이 문서에서 선택한 단계만 읽는다. 명령 예제의 기준 작업 폴더와 인라인 리소스 경로는 상위 스킬 루트다. Markdown 링크는 이 파일 위치를 기준으로 한다.

## 권한 오류를 진단하고 정식으로 보완하기

- 계정 소유권, 현재 도구의 로그인 신원, OAuth/API token scope, 대상 zone/account, 명령별 필요 권한을 따로 판정한다. 인증 오류 한 번으로 소유자 권한이 없거나 누군가 권한을 회수했다고 단정하지 않는다. 누가 바꿨다는 설명은 감사 로그 등 행위자 근거가 있을 때만 한다.
- 기존 Wrangler whoami와 login --scopes-list 및 공식 endpoint의 accepted permissions를 대조한다. 배포 성공은 모든 도메인 설정 변경 권한을 의미하지 않는다. ssl_certs:write도 Zone Settings Write를 대신하지 않는다. 지원 scope에 없는 권한은 재로그인 반복으로 해결된다고 안내하지 않는다.
- 권한 부족이면 기존 정상 관리 경로를 먼저 찾고, 사용자 요청과 현재 도구의 승인 규칙 안에서 정식 부여한다. 예를 들어 Zone Settings 변경용 token은 해당 zone의 Zone Read와 Zone Settings Edit로 한정할 수 있다. 기존 배포 OAuth를 취소하거나 전역 환경 변수에 광범위 token을 덮어쓰지 않는다.
- 신규 token 발급·보관·연결은 보안 작업이다. 최종 발급/권한 확대 시 도구가 요구하는 확인·사용자 직접 입력 경계를 지킨다. token은 대화·로그·Git·공유 스킬·보고서로 출력하지 않고 승인된 호스트 보안 저장소에서만 소비한다.
- 서버의 일반 파일 Permission denied는 관리자 명령의 거절과 다르다. 기존 실행 문서가 지정하고 사용자가 승인한 sudo/controller의 허용 상태를 먼저 조회한다. 새 계정, 새 SSH 키, 광범위 chmod, 무제한 sudo 권한 추가로 해결하지 않는다. 정식 관리자 명령 자체가 거절되면 우회하지 말고 원 거절·필요한 정확 권한·해제 담당을 기록한다.
- 대상·실제 오류·허용/미허용 작업·정상 부여 방법·실제 반영 범위·남은 일을 쉬운 말로 보고한다. 설치/권한 부여/작업 성공은 별도 증거이며 원인이 뒤집히면 기존 HOLD 설명을 명시적으로 정정한다.
