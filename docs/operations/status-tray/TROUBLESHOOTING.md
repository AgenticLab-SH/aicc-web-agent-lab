# AICC 문제 해결 및 RDC 계정 전환

상태 트레이의 **도구**에서 **AICC 문제 해결**, **RDC 계정 전환**을 연다. 기존 WinForms 트레이와 자동 시작 작업을 사용한다.

## AICC

- 상태 조회는 현재 게이트웨이 세대의 실행·미확인·재연결 수를 표시한다. 정상 상태는 `OPEN`이다.
- 진단 복사는 상태와 미확인 호출 ID를 복사한다. 코덱스에 붙여 넣어 기존 요청의 재전송 없이 복구를 이어간다.
- 준비된 복구 적용은 읽기 실패, 실행 작업 없음, 원 기록 백업, 정확한 프로세스·설정 일치, 새 독립 READY가 모두 있어야 열린다. 만료된 READY와 이미 시도한 계획을 재사용하지 않는다.
- 쓰기 결과 불명, 진행 중인 정비, 다른 프로젝트 자식 서비스가 있으면 해당 담당과 범위를 먼저 조정한다. 원 검색을 다시 보내거나 unknown을 임의로 지우지 않는다.
- 운영 도구는 `Invoke-AiccTroubleshooter.ps1`의 `Status`, `Prepare`, `Repair`, `Rollback`이다. `Prepare`에는 관리형 gateway 릴리스와 고유 operation directory가 필요하다. `Repair` 전 새 계획의 challenge·SHA256·만료와 일치하는 독립 `ready.json`이 필요하다.

2026-10-19 장애에서는 Workspace 검색의 시간 초과가 전체 게이트웨이를 DRAINING 상태로 막았다. 별도 private gateway 어댑터에서 검토된 읽기 메타데이터만 사용해 읽기 실패를 격리했다. 실패한 정확한 요청의 재전송과 같은 lease의 쓰기는 보류하며, 다른 lease의 같은 읽기 도구와 별도 provider는 계속 사용할 수 있다. 과거 기록처럼 scope가 없으면 보수적인 보류를 유지한다. 쓰기 결과 불명은 전체 정지를 유지한다. 원 시간 초과의 최초 원인이 완전히 제거됐다는 의미는 아니다.

## 여러 지피티의 병렬 사용

- provider마다 최대 4개를 동시에 전달하며 실행·대기를 합쳐 최대 36개를 접수한다. 같은 lease는 대기 8개를 상한으로 둔다. 대기 제한은 30초다. 초과·취소·기한 만료는 실제 전달 전 거절하며 자동 재전송하지 않는다.
- 같은 lease의 쓰기는 순서대로 전달한다. 다른 lease는 독립적으로 진행하고, 같은 작업공간·겹치는 경로의 단일 작성자 잠금과 쓰기 request ID 중복 방지는 기존 Workspace authority가 계속 맡는다. 단순히 다른 지피티 대화라는 이유로 같은 원본에 동시 쓰기를 허용하지 않는다.
- 대기 중인 요청도 정비 accounting에 남는다. 새 정비의 begin은 새 요청을 막고 실행·대기·unknown·reconnecting이 모두 비었을 때만 consume할 수 있다.
- 실패 격리에는 인수·lease 원문 대신 요청 및 scope SHA256만 남긴다. 로그가 누적되면 전체 상태 checkpoint와 이전 메타데이터 구간을 보존하며 회전해 정상 장기 사용이 단일 로그 용량 한도로 중단되지 않게 한다.

## RDC

트레이의 RDC 계정 전환에서 자동 순환 시작, 다음 계정, 자동 순환 중지와 저장 계정 선택을 사용할 수 있다. 상태는 2초 간격으로 operation ID·단계·대상과 안내를 갱신한다. 전환 잠금을 잡아도 상태 읽기는 계속 가능하다.

- `aicc-rdc`는 단일 순환 담당을 시작한다. 기존 RDC 로그인 자동 시작에도 연결된다.
- `aicc-rdc -Action Next`는 다음 계정으로 넘긴다. 기본 순서는 owner 설정의 세 계정이며 소진·기준 이하·미확인·오래된 한도 관측 계정은 건너뛴다. 소진 기록이 오래되었다는 이유로 복귀시키지 않는다.
- `aicc-rdc -Action Status`는 원 operation의 진행과 대상 신원을 읽는다. 병렬 요청은 같은 operation을 반환한다.
- `aicc-rdc -Action Stop`은 감시만 중지한다. 작업 프로세스는 종료하지 않는다.

PC 로그인은 Windows CurrentUser DPAPI로 저장하고, 지피티의 공식 계정별 OAuth 연결은 모두 유지한다. 매 호출에 현재 지피티 도구 명세의 해당 계정 `link_id`를 사용한다. 연결 ID는 지피티마다 다를 수 있으므로 이메일·실제 who_am_i 사용자 ID로 대조한다. 다음 계정 사용을 위해 기존 연결을 해제하거나 플러그인을 재설치하지 않는다. 최초 연결만 Connect의 공식 UI와 Google 로그인을 사용한다.

평상시 hotRotate는 로컬 MCP child·터미널을 유지하고 RDC 중계만 바꾼다. 실행 중·원격 pending/executing·결과 불명·오래된 관측이면 보류한다. 관리형 종료 ACK는 최초 유지보수/재시작 절차이며 평상시 전환에서 로컬 core를 종료하지 않는다. 토큰 회전은 저장 별칭에도 보존하고 인증정보·도구 인수/결과를 진단 로그에 남기지 않는다.

지피티는 who_am_i의 실제 잔여 비율을 Observe로 전달한다. 월 한도에 의한 실제 거절이면 UsageRejected를 함께 전달할 수 있다. 공식 화면 사용량 읽기도 별도 자식에서 수행해 전환 요청을 막지 않지만 다른 로그인 신원이면 UNKNOWN이며 지피티 신호를 기다린다. 경고만으로 실패나 플러그인 단절로 오인하지 않는다.

전환 전 지피티가 전환 중이라고 알리고, 독립 AICC Status를 읽는다. VERIFYING 뒤 현재 명세에서 대상 연결을 찾아 who_am_i·온라인 기기·승인된 최소 읽기에 성공한 경우만 Confirm하여 READY를 만든다. 새 연결이 현재 턴의 도구 명세에 없으면 읽기 미확인으로 남긴다. Reconcile은 정확한 중계 ACK를 대조해 UNVERIFIED로 남기고 다음 명시 전환을 허용하며 READY를 만들지 않는다. 원 응답이 미전환이고 동일 agent instance·기존 기기·CONNECTED·active=0·unknown=0이 모두 신선하면 NOT_SWITCHED로 조정한다. 불명 교체 요청은 반복하지 않는다.

`Install-AiccRdcRotation.ps1`은 owner 설정을 받아 immutable runtime·핀·복구본·명령을 설치한다. 개인 계정·경로·연결 ID는 공개 소스에 내장하지 않는다. 변경된 controller만 정상 중지하고 시작하며 agent 변경 때만 정상 관리형 재시작을 요청한다.
## 적용 및 확인 기록

2026-10-19: 관리형 트레이 설치, 두 도구의 실제 상태 화면, AICC 새 gateway의 `OPEN` 및 공식 Workspace 목록 호출 성공을 확인했다. 24개 동시 읽기의 결과 구분, 같은 lease 쓰기 직렬화, 요청/scope별 실패 격리, 대기 취소·만료의 무전달, 로그 회전 검사를 통과했다. RDC는 공식 계정 화면과 서버 사용자 응답을 대조해 요청한 계정을 확인하고 암호화 저장했다. 저장 계정 전환 도구로 이전 계정에서 요청 계정으로 실제 전환하고 `CONNECTED`를 확인했다. 서로 다른 실제 지피티 대화들의 장시간 부하 검증은 미실행이다.

정비 전 원본과 미확인 기록은 사용자 상태 루트의 `backups/troubleshooter`에 보존한다. 복구 중 다른 서비스가 잠시 중단되면 명시적으로 승인된 서비스만 기존 명령으로 복원한다. 이번 실제 정비 snapshot에는 FBTT/Python 프로세스가 포함되지 않아 그대로 보존했고, FBTT `localhost:3927`과 Python `192.0.2.1:8765`에서 HTTP 200을 확인했다. FBTT는 IPv6 loopback에 바인딩되어 IPv4 주소만으로는 확인할 수 없다.

### 2026-10-19 후속 적용과 전환 시험

세 계정의 공식 지피티 연결 목록 추가, 단일 `aicc-rdc` 실행기와 자동 시작, 트레이 순환 제어, 기존 서비스 제어 스킬의 계정별 link_id·안내·확인 절차를 적용했다. 로컬 AICC/활성 Codex 배포에 이어 Web 네이티브 **서비스 웹 제어**도 기존 비공개 GitHub·Notion 양쪽 바이트 백업 VERIFIED 후 설치했다(immutable ID `00000000000000000000000000000000`, HTTP201, installed_verified). 등록된 참조와 기존 sync manifest 연결을 확인했으며 실제 GPT 로드와 구분한다.

기존 1 → 2 → 3 → 1 시험은 재사용한다. 2번은 잔여0%·실제 월 사용량 거절이므로 명령 성공으로 처리하지 않는다. 후속의 새 도구 명세에서 세 계정 신원·link_id를 Bind했고 3번 실제 who_am_i·온라인 기기·REPL 읽기·Confirm READY를 통과했다. 같은 agent PID/instance와 REPL PID·메모리를 유지한 1↔3 두 차례 왕복, 동시 Next4개가 단일 operation을 반환하는 시험, 인수 없는 Next가 소진2번을 건너뛰는 시험을 완료했다. 시험용 REPL은 1275초 뒤 exit0으로 종료했다. 최종 계정은1번이다.

요청된 실제 지피티 두 Chat의 병렬 시험은 새 대화의 composer_not_empty로 전송 전 보류됐다. 사용자 미전송 초안을 지우지 않았고 두 요청의 submissions=0을 기록했다. 네이티브 실제 GPT 로드·GPT 자체 자동 왕복·여러 지피티 장시간 부하는 미확인이다. 빈 exact Chat을 준비할 수 있을 때 원 수락 시험을 재개한다. 범위 밖 전체 회귀 검증 미실행. 계정/원 요청/모델 route를 초기화하지 않는다. 상세 절차는 [RDC 연속성 참조](../../../guidance/skills/build-web-service-control/references/rdc-continuity.md), 실제 영수증은 owner 상태의 backups/troubleshooter/rdc-rotation-20261019 및 asset-control/rdc-continuity-20261019에 둔다.

## RDC 한도 조회와 자동 복귀 · 2026-10-19

- `aicc-rdc -Action Quota`: 계정별 잔여 비율·관측 시각·출처·제외 사유·공식 초기화·다음 확인 시각을 읽는다. KST 표시를 함께 반환한다.
- `aicc-rdc -Action Quota -Refresh`: 세 계정의 공식 사용량 재조회를 접수한다. `-Profile account2`는 반환 표시 범위를 좁힌다. 접수 뒤 Quota의 관측 시각·checkPhase를 본다. 접수는 조회 완료가 아니다.
- `aicc-rdc -Action Status`: 전환 operation과 quota 풀을 함께 읽는다. 기존 트레이의 RDC 상태 조회도 풀 요약을 표시하도록 연결했다.

단일 감시기는 사용 가능 계정을5분마다, 제외 계정을6시간마다 공식 웹 세션으로 차례로 조회한다. 같은 계정의 공식 resetsAt가 먼저 오면 그 직후에 확인한다. 초기화가 도래하거나 데이터가 오래됐다는 이유만으로 제외를 해제하지 않는다. 신원이 일치하는 잔여가 기준10%를 넘으면 다음 순환 후보에 복귀한다. 정확한 초기화 시각을 읽지 못하면 미확인으로 표시한다. 지정 계정 전환도 제외 규칙을 따른다.

모든 후보가 소진·미확인이면 QUOTA_WAIT로 기존 연결을 유지한다. 공식 회복 관측 후에만 전환을 진행하며 사용자 중지·불명 결과 HOLD·보안 거절은 자동 해제하지 않는다. 조회가 실패해도 마지막 소진 기록은 유지된다. 브라우저 표시 계정 전환은 기존 Google 로그인만 사용하고 PC의 RDC 중계·지피티의 기존 OAuth 연결을 해제하지 않는다. 대상 로그인·MFA가 필요하면 해당 상태를 남기고 비밀번호나 인증 비밀을 저장하지 않는다.

이 변경은 controller 8a99010599ed87ce 설치·감시 시작 요청과 로컬/네이티브 스킬 본문 반영까지 수행했다. 새 코드 사후 검증은 미실행이다. GPT가 네이티브 스킬을 실제 호출해 전환하는 수락은 기존 사용자 초안 보존 HOLD를 유지한다.
